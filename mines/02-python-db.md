## 조용한 실패 — 실패가 성공처럼 보이는 구조 (총론)

예외가 안 나고 로그도 안 남는다. 하루에 다섯 건이 이 형태였던 날도 있었다.

| 액면 신호 | 실제 |
|---|---|
| CI 그린 | 실동작 아님 |
| 검색 결과 0건 | 봇 차단 페이지(2KB) |
| 진행 파일에 `ok:225` | 자기가 만든 껍데기를 다시 읽었다 |
| `PUT 200 SUCCESS` | 값이 안 바뀜. 6주간 무효 |
| 함수가 "전건 미발견" | 튜플을 문자열처럼 다뤘다 |
| 크론이 정상 종료(0) | 가드가 자기를 잡아 한 번도 안 돌았다 |
| `registered: true, reason: null` | 이미지 0장 |
| 문서의 "전량 삭제 완료" | 68건 잔존 |

**원칙 — 판정 전에 원자료를 본다**
- 0건·미발견·성공플래그는 **결론이 아니라 관측**이다. 그 관측이 나온 경위를 먼저 본다
- 요약·상태 문구가 아니라 **원본 필드**를 읽는다
- "완료"라고 찍혔는지가 아니라 **몇 개가 나왔는지** 센다
- **응답 크기·타입을 검사한다.** `len < 임계`거나 예상 타입과 다르면 실패로 간주한다

**Traceback만 남고 `"신규 0"`조차 안 찍히면, 죽은 것과 없는 것이 구분되지 않는다**
알림 배치가 외부 데이터의 필드 하나에 대괄호 접근(`rec['url']`)을 하다 KeyError로 죽었다. 로그에는 Traceback뿐이고, 정상 회차가 찍던 `"신규 0"`마저 없다. **"오늘 주문이 없었다"와 "배치가 죽었다"가 로그로 같은 모양**이다.
- **배치 시작·종료에 한 줄씩 찍는다.** `"신규 0"`이라도 찍혀야 죽은 것과 없는 것이 갈린다
- **외부 데이터의 필드는 전부 선택적이라고 가정한다.** `.get()`으로 접근한다. 대괄호 접근은 한 건만 없어도 전체 회차를 죽인다

## "없음"과 "못 찾음"은 다른 사실이다

**증상**
조회 결과 0건. 여기서 갈라지는 두 해석이 **정반대 결론**을 만든다.

| 관측 | 해석 A (없음) | 해석 B (실패) |
|---|---|---|
| 검색 0건 | 그 대상이 없음 | **무작위 봇 차단** |
| 메일 0건 | 새 메일 없음 | **SINCE·LIMIT 필터에 걸림** |
| 카탈로그에서 항목 미발견 | 단종 | **페이지를 덜 긁음** |
| 배치 처리 0건 | 대상 없음 | **대상 목록의 소스가 다름** |
| 텍스트 0자 | 본문 없음 | **본문이 이미지 태그뿐** |
| `products.json` 404 | 카탈로그 없음 | **그 플랫폼이 아닐 뿐** |
| 도메인 미발견 | 사이트 없음 | **추측으로 두드렸을 뿐** |
| 집계에 "카탈로그 없음" | 수집 안 됨 | **수집은 됐는데 매핑 테이블에 미등록** |

**판별법**
- **응답 크기를 본다.** 정상 응답이 2KB일 수 없는 자리에서 2KB가 오면 실패다
- **조건을 하나씩 푼다.** 기간·건수·상태·타입을 넓혀 **0이 유지되는지** 본다
- **다른 경로로 교차 확인한다**
- **모수를 함께 센다.** `0/N`에서 **N을 모르면 0의 의미도 모른다**

**대가**
이 구분을 안 해서 사흘간 치른 값: 4개 로케일 "재고 없음" 오판 · 메일 12건을 0건으로 판정(3회 반복) · 배치 대상 0건 · "단종" 판정(실제로는 도메인이 달랐다).

**차단은 회차·로케일마다 무작위라 단발 조회로는 판정할 수 없다**
같은 쿼리를 두 번 돌렸는데 1회차는 한 로케일만 성공(1.1MB)하고, 2회차는 그 로케일만 실패(2.2KB)하고 나머지가 성공했다. 로케일 고정 문제가 아니라 **요청 단위 무작위**다. 4개 로케일 0건으로 "소싱처 없음"을 판정한 것이 전부 재검증 대상이 됐다.
- 결과를 믿기 전에 **`len` 임계(50KB 미만이면 차단) + 핵심 마커(결과 항목 태그) 존재**를 같이 검사한다
- 실패면 **지수 백오프 재시도**(6/12/18초, 4회)
- ★ **재시도로 이기려 들지 않는다.** 같은 소스에서 이미지 수집도 같은 차단으로 0장이 반복됐다. 차단 안 되는 다른 소스(자체 시스템에 이미 등록된 원본)가 있으면 **그쪽으로 피벗**하고, 차단되는 소스는 폴백으로 강등한다

**메일 0건·크래시·미추출 — 수집기 전환에서 한 번에 밟은 것들**

| 증상 | 원인 | 해법 |
|---|---|---|
| 주문번호 미추출 | 정규식 `{6,20}` — 어떤 거래처는 **5자리** | ID 길이를 가정하지 않는다. `{4,20}` |
| 크래시 | 헤더 charset `unknown-8bit` → 디코더 예외 | utf-8 → cp949 → euc-kr → latin-1 **폴백 체인** |
| 메일 0건 | `SINCE 7일` · 최근 120통이 코드에 기본값으로 박힘 | 기본값은 **환경변수**로 뺀다 |

★ **ID 길이·문자셋·조회 기간은 전부 상대 쪽의 사실이다.** 내 코드에 박은 가정은 상대가 바뀌는 순간 0건이나 크래시로 나타나고, 0건은 정상처럼 보인다.

**수집은 됐는데 집계가 "없음"이라고 한다**
카탈로그를 수집해 놓고 브랜드 매핑 테이블에 안 넣으면 집계는 "카탈로그 없음"을 보고한다. 상위 25개 브랜드가 전부 ✘로 나왔는데 실제로는 여럿이 이미 카탈로그에 있었다. **수집과 매핑은 별개 작업이다.** 수집 직후 매핑 테이블에 등록하는 것까지가 수집이다.

## 반환 스키마를 가정하면 조용히 헛돈다

**증상**
`h = get(...)` 로 받아 `in`·정규식·길이 검사를 걸었는데 **전건 미발견**으로 나온다. 예외는 안 난다.

**원인**
`get()`이 `(status, body)` **튜플**을 돌려주고 있었다. 튜플에 `in`을 걸면 원소 동등성 검사가 되어 항상 False, `len()`은 2가 된다. 문법적으로 전부 유효해서 아무도 안 죽는다.

**해법**
`status, body = get(...)` 로 언패킹. 그리고 **반환 스키마를 가정하지 말고 한 번 찍어보고 쓴다.**

**검증**

```python
print(type(r), repr(r)[:200])
```

진행 파일·집계 대상도 마찬가지다. `list(d.items())[:3]`으로 값 스키마를 먼저 본다. 스키마를 가정하고 돌린 집계는 0을 내놓고, **0은 "데이터 없음"으로 오독된다.**

## 진행 파일에 결과를 안 남기면 사후 검증이 불가능해진다

**증상**
`*_done.json`이 `{id: true}`만 기록해 **무엇을 썼는지 남지 않는다.** 나중에 불량이 발견됐을 때 완료 2천여 건 중 몇 건이 불량인지 로컬에서 셀 수 없다.

**해법**
done 파일에 최소 3필드: `{id: {ts, len, src}}` — 생성 본문 길이와 원본 출처만 있으면 사후 전수 검증이 로컬에서 끝난다.

**★★ 접두 형식을 쓰면 판정 연산자가 바뀐다**

값에 사유를 남기려고 접두 형식을 쓰는 건 좋다 — 무엇을 왜 그렇게 처리했는지가 남는다.

```
done[x] = "ok:1234567890" / "skip:정책제외" / "manual:검토필요" / "fail2"
```

**그러면 판정은 반드시 `startswith`여야 한다.**

```python
done_ok = str(v).startswith(("ok", "skip", "manual"))
```

★ **`!= "ok"` 나 `not in ("ok", "skip")` 은 접두 형식에서 항상 통과한다.**
`"ok:1234567890" != "ok"` 는 **True**다 → **완료된 건을 매 회차 재처리한다.** 에러는 없고, 로그는 정상이고, **목록만 영원히 안 비운다.**

**더 안전한 형태 — 판정 대상과 설명을 분리한다**

```python
done[x] = {"state": "ok", "detail": "1234567890"}
```

값 하나에 두 정보를 담으면 **읽는 쪽이 매번 파싱 규약을 지켜야 하고, 한 곳만 틀려도 샌다.**

**같은 연산자 위험의 반대 방향**

| 값 체계 | 틀린 연산자 | 결과 |
|---|---|---|
| `"ok:123"` | `!= "ok"` | 완료를 미완료로 읽어 **무한 재처리** |
| `임시저장` / `임시저장중` | `== "임시저장"` | 해당 건을 **누락** |

★ **접두어를 공유하는 값 체계에서는 `==`도 `!=`도 둘 다 위험하다.** 한쪽은 빠뜨리고 한쪽은 다 통과시킨다.
★ **값 형식을 정할 때 판정 코드를 같이 정한다.** 나중에 형식만 바꾸면 판정이 조용히 뒤집힌다.

**★★ `continue` 전에 저장하지 않으면 판단이 사라진다**

루프 안에서 **상태를 메모리에만 바꾸고 `continue`** 하면, 그 회차가 죽거나 다음 저장 전에 끊겼을 때 **판단한 사실 자체가 없어진다.** 다음 회차가 같은 건을 처음 보는 것처럼 다시 처리한다.

★ **상태를 바꾸면 그 자리에서 저장한다. 루프 끝 저장만 믿지 않는다.**

이건 "실패도 기록해야 한다"와 **한 겹 다르다** — 저기는 **기록할 생각을 안 한 것**이고, 여기는 **기록했는데 안 쓰인 것**이다.

**★★ 네 형태가 전부 같은 증상을 낸다**

같은 진행 파일 하나를 두고 네 가지 방식으로 틀렸다. **하루에 넷 다 밟았다.**

| | 형태 | 증상 |
|---|---|---|
| ① | 값 형식을 바꾸고 판정부를 안 고침 | `"ok:123" != "ok"` 통과 → 완료를 재처리 |
| ② | `==` 로 판정 | 접두어를 공유하는 값을 누락 |
| ③ | 응답만 보고 `ok` | 재조회 검증 없음 → **완료 기록이 통째로 허수** |
| ④ | `continue` 전에 저장 안 함 | 판단이 사라져 **무한 재처리** |

★ **넷 다 에러가 없고, 넷 다 목록이 안 빈다.**
그래서 **하나를 고쳐도 증상이 남으면 "안 고쳐졌다"가 아니라 "다른 형태가 또 있다"로 읽어야 한다.**

**규약 — 셋 다 필요하다**

1. **판정은 `startswith`** — 접두 형식이면 `==`·`!=` 둘 다 위험하다
2. **저장은 즉시** — 상태를 바꾸면 그 자리에서
3. **완료는 재조회로 확인** — 응답은 증거가 아니다

★ **셋 중 하나만 빠져도 목록은 안 빈다. 그리고 어느 게 빠졌는지는 증상으로 구분되지 않는다.**

**같이 밟는 것 — "처리 못 함"과 "처리 필요 없음"의 혼동**
실패를 `done`에 안 남기면 **무한 재시도 루프**가 된다. 반대로 "이미 처리할 필요가 없어진 건"을 미처리로 분류하면 목록이 영원히 안 비고 배치가 20분마다 같은 일을 반복한다(로그만 385KB 쌓였다).
→ **실패도 기록하되, 두 상태를 구분해 기록한다.**

## 폴백 체인에서 앞단이 `continue`하면 뒷단이 전부 죽는다

**증상**
폴백을 4단 쌓았는데 100여 건이 "원본 없음"으로 기록됐다. 실제로는 회복 가능한 건이었다.

**원인**
1단(웹검색) 실패 시 `done[id]="nourl"; continue` — 그 아래 2·3·4단이 **한 번도 실행되지 않았다.**

**핵심**
진행 파일의 실패 사유는 **어느 단계에서 나갔는지**를 말할 뿐, "모든 수단을 다 썼다"를 뜻하지 않는다. 실패 코드를 근거로 처방을 정하기 전에 **그 코드가 찍히는 지점이 체인의 어디인지** 확인한다.

## 성공 응답에 "핵심 산출물 0개"가 섞이면 성공이 아니다

**증상**
등록 47/47이 `registered: true`, `reason: null`로 전부 성공. 그런데 **전량 이미지 0장**이었다. 실물을 눈으로 볼 때까지 아무도 몰랐다.

**원인**
외부 데이터의 형식을 가정했다. 엔트리가 `{name, sources:[{url, priority}...]}` 구조인데 `v.get("url")`로 flatten해서 전부 `None`이 됐다. URL이 빈 문자열이 되니 수집이 아예 안 돌았고, 그래도 등록 자체는 성공했다.

**해법**
- 성공 + `image_count == 0`이면 `warning` + 상단 집계로 **표면화**한다
- 외부 데이터 **형식 가정 금지** — 실제 1건 열어보고 키를 확인한다

**규율**
수집=이미지, 등록=이미지, 번역=번역본 — **"있어야 할 것 0개"는 조용히 넘기지 않는다.**

**빈 레코드가 가격만 얹은 채 등록을 통과해 판매까지 갔다**
스크래핑이 실패한 잔재 — 본문도 속성도 없는 레코드 — 에 가격 하나만 붙어 등록 검증을 통과했고, 판매중 상태로 발견됐다. 주문이 들어오면 **발주 자체가 불가능**하다. 소싱처 미연결은 "어디서 사는지 모른다"지만 이건 **상품이 없다.**
빈 레코드의 네 가지 지표(정상 건과 대조):
1. **이미지가 해시 파일명 1장** — 정상은 벤더 코드 파일명 + 모델컷 2장 이상
2. **속성 전량 공란**, 본문 비어 있음
3. 옵션이 **자리표시 문구**(`"상세설명 참조"`)
4. **고시정보 양식이 카테고리와 불일치** — 폰 액세서리인데 자동차부품 양식

★ 등록 검증에 "가격 있음"만 있고 "핵심 산출물 있음"이 없으면, 실패 잔재가 정상 건과 같은 문을 통과한다.

## "완료" 기록이 완료를 뜻하지 않는다

**증상**
천여 건이 `ok`로 기록됐는데 표본 40건이 전부 원본 그대로였다. `ok`의 근거는 `status_code == 200` 하나였다.

**해법**
완료를 적을 때 **무엇으로 검증했는지 같이 적는다** — `재조회 N건` / `전수 재조회` / `미검증`.
검증 안 한 완료는 **"실행함"이라고만 적는다.**

성공 판정을 함수로 강제한다.

```python
def ok(code, resp):
    return code == 200 and isinstance(resp, dict) and resp.get("code") != "ERROR"
```

이걸 안 넣어 700여 건을 헛돌렸다. 전부 거부됐는데 진행 파일에는 `put`으로 기록됐다.

**오염된 완료 목록은 다음 작업의 모수까지 틀리게 한다**
교정 배치가 `PUT 200 SUCCESS`만 보고 2,608건을 `ok`로 적었다. 전수검증 표본 **60건 중 60건이 미반영.** 이 2,608건은 완료로 집계돼 **다음 회차의 남은 대상 산정에서 빠져 있었다** — 허수가 한 배치의 문제로 끝나지 않고 그 뒤 작업의 분모를 오염시킨다.

강제 규약:

```
쓰기 → 대기 → 재조회 → 값 대조 → 일치할 때만 ok
```

- 전수 재조회가 비싸면 **회차마다 표본을 뽑아 검증**하고 그 비율을 같이 기록한다
- 표본이 **전건 미반영이면 즉시 중단**한다. 60/60이 그 신호였다
- ★ **응답 기반 `ok`와 재조회 기반 `ok`를 같은 필드에 쓰지 않는다.** 섞이는 순간 어느 것이 검증된 완료인지 알 수 없게 된다

**증상**

**해법**

## 같은 값을 두 경로가 각자 계산하면 갈라진다

**증상**
"화면엔 맞게 나오는데 전송/저장만 0 또는 빈값."

**원인**
검수 화면(GET)과 실제 전송(POST)이 **각자** 같은 빌더 함수를 호출했다. 한쪽만 환율 파라미터를 주입해서, GET은 수십만 원대 가격을 표시하고 POST는 `None` → `int(None or 0)` → **0을 전송**했다.

**판별**
- 같은 도메인 값(가격·분류·키)을 **두 군데 이상에서 만들고 있나?**
- 두 호출부의 **인자 목록 차이**가 곧 갈라짐의 크기다

**처방**
1. **단일 소스 헬퍼**로 묶는다
2. 파생값은 **한 번 계산해 넘긴다**
3. **미확정을 0으로 강등하지 마라.** `int(x or 0)`은 "모름"을 "0"으로 둔갑시켜 조용히 전송한다
4. 계약 테스트로 **표시값 == 전송값**을 못 박는다. 양쪽을 따로 검증하면 갈라짐을 못 잡는다

**두 경로만이 아니라 정본과 사본도 갈라진다**
소싱 맵의 `krw`가 마켓플레이스의 실제 등록가와 달랐다. 등록가는 마켓플레이스가 정본이고 로컬 맵은 사본이다 — **사본을 근거로 마진을 계산하면 틀린다.** 갈라지는 건 코드 경로 두 개만이 아니다. "정본 시스템 vs 로컬 복사본"도 같은 형태다.
같은 맵에서 6,541건 중 618건은 `usd`·`jpy`가 모두 비어 있었다. 소싱처가 연결돼 있어도 **가격이 없으면 마진 검사에서는 미연결과 같다.** 필수 입력이 빠진 레코드는 링크가 없는 레코드와 동치로 취급한다.

**상류 값 0이 파생값을 음수로 만든다**
한 채널의 판매가 필드가 0인 상품이 있었다(임시 실패 상태 등). 이걸 그대로 가져와 다른 채널 가격을 `원가 − 랜덤`으로 파생하면 **음수 가격**이 나온다. 파생 공식은 상류가 정상값이라는 가정 위에 서 있다 — **하한 검증을 파생 직전에 건다.** 0은 "값이 있다"가 아니라 "값이 없다"의 다른 표기일 수 있다.

## 배치 진행률을 전체 비율로 읽으면 안 된다

**증상**
배치를 돌리며 로그를 보니 실패가 **8건뿐**이었다. "거의 다 됐다"고 판단했다.

**원인**
그건 **배치 앞 구간만 돈 결과**였다. 구간을 건너뛰며 다시 재보니 분포가 전혀 달랐다.

| offset | 성공률 |
|---|---|
| 0~4,000 | **92~95%** |
| 6,000 | **44%** |
| 8,000 | **0%** |
| 9,400 | **84%** |

**전체는 68.3%였다.**

★★ **정렬 순서가 편향을 만든다.** 등록순으로 정렬하면 **앞 구간은 최신 데이터라 잘 정비돼 있다.** 앞만 보고 전체를 추정하면 항상 낙관 쪽으로 틀린다.

**해법**
- **offset을 건너뛰며 표본을 뽑는다.** 앞에서 N건이 아니라 **구간마다 N건**
- 진행률 로그에 **어디까지 처리했는지**를 같이 찍는다. `"실패 8건"`만으로는 모수를 모른다
- ★ **0%인 구간이 있는지 본다.** 평균은 그런 구간을 숨긴다

같은 형태를 표본 크기에서도 겪었다. 같은 조사를 세 번 했는데 **세 번 다 같은 방향으로 틀렸다.**

| 표본 | 불량률 |
|---|---|
| 500 | 36% |
| 1,900 | 48% |
| 4,900 | **69%** |

★★ **추정이 계속 한 방향으로만 갱신되면, 그건 아직 수렴하지 않았다는 뜻이다.**
표본을 키울 때마다 나빠지고 한 번도 반대로 안 갔다면, **지금 값도 아직 하한이다.**
**작은 표본과 앞쪽 표본은 둘 다 낙관 쪽으로 틀린다.**

## 키 정규화는 양방향을 다 봐야 한다

같은 대상을 가리키는 키가 어긋나는 방식이 **두 방향**이다. 한쪽만 고치면 반대쪽이 그대로 남는다.

| 방향 | 원인 | 증상 |
|---|---|---|
| **다른 것 → 같은 키** | 절단으로 접미가 잘려나감 | 덮어써서 **마지막 것만 남는다** |
| **같은 것 → 다른 키** | 재등록 때마다 **접미가 붙는다** | 조회가 **아예 안 붙는다** |

**두 번째 방향의 실제 모습**

```
B0XXXXXXXX → B0XXXXXXXXAB → ...R / RR / RRR
```

재등록·재생성 때마다 접미가 하나씩 붙는다. 사람이 보면 같은 물건인데 키로는 완전히 다르다.

**해법**
1. **접미·접두를 전개해 후보를 만든다** — 원본 / 접미 제거 / 접두 제거
2. **소문자·특수문자 제거 인덱스**로 **교차 조회**한다

적용 후 8,858건 중 6,657건(75%)이 붙었다.

★ **전개로도 안 붙는 게 남는다** — 아예 다른 채번 체계로 만들어진 키다. **채번 시점에 대응 키를 같이 박지 않으면 사후 복구가 안 된다.** 생성과 등재를 같은 코드에서 처리한다.

**첫 번째 방향의 실제 모습 — 덮어쓰기는 "미색인"으로 남는다**
외부 SKU가 소스 핸들의 38자 절단이라 변형끼리 같은 키가 된다. `index[key] = id`로 넣으면 **마지막 것만 남고 나머지는 영원히 미색인**이다. 처리에 실패한 게 아니라 **색인에 자리가 없다.**
- `key → id`는 **1:N**이다. 1:1을 전제한 dict가 틀렸다 → `id → key` 역인덱스를 따로 두고, 정방향은 리스트로 받는다
- 적용 후 미색인 2,443 → 2,143. 300건이 데이터를 건드리지 않고 즉시 해소됐다

★ **"미색인 N건"이 회차마다 안 줄면 처리 실패가 아니라 키 충돌을 의심한다.** 정체된 지표는 "일이 안 됐다"가 아니라 **"일이 담길 곳이 없다"**일 수 있다. 처리는 매번 정상 종료하고 숫자만 안 움직인다.

절단 길이는 시스템마다 다르다:

| 지점 | 절단 |
|---|---|
| 마켓플레이스 A의 외부 SKU 저장 | **20자** |
| 로컬 색인 키(소스 핸들) | **38자** |
| 마켓플레이스 B의 판매자 관리 코드 | **30자 제한** |

"절단됐다"만 알면 부족하다. **몇 자에서 잘리는지가 충돌 범위를 정한다.** 같은 데이터가 채널마다 다른 지점에서 잘려 충돌 집합이 서로 다르다.

**키 전개는 조회하는 쪽 전부에 넣는다**
접미·접두 전개를 여섯 개 배치 중 다섯에만 넣으면, 빠진 하나는 **그 배치만 영원히 미매칭**을 낸다. 처방이 정해진 것과 모든 호출 지점에 들어간 것은 별개다. `grep`으로 조회 함수 호출부를 전부 세고 나서 끝났다고 한다.

## 식별자를 쓰기 전에 두 가지를 확인한다

**필드를 식별자로 쓰기 전:**

1. **유일한가** — 값이 겹치지 않는가
2. **식별용인가** — 그 필드가 **대상을 지목하려고 존재하는가**

**①만 보고 ②를 안 보면** 태그 같은 검색용 필드를 키로 쓴다.
**②만 보고 ①을 안 보면** 정식 식별자에 절단·부모공유로 당한다.

| 쓴 필드 | 깨진 조건 |
|---|---|
| 외부 SKU 필드 | **①** — 20자에서 절단 저장. 중복이 전체의 **40%대** |
| 상품 이름으로 인덱싱 | **①②** — 상태 파일이 섞여 본문 없는 껍데기가 선점 |
| 상품명 매칭 | **②** — 3연속 사고 |
| 플랫폼 `tags` | **②** — 검색용 롱테일. 태그 하나로 품목 오분류 |
| 진행 파일명 | **①** — 다른 스크립트가 **다른 형식으로 같은 이름** 사용 → 200여 건 유실 |
| 카테고리 **이름** | **②** — 부분일치 오탐. 리프 **ID**로 고정해 해결 |
| 한 레코드의 두 필드 | **①** — 키와 URL이 **서로 다른 대상**을 가리킴 |
| 메일 발신 도메인 | **②** — 대행 발송 인프라의 도메인이라 모든 스토어가 같은 값. **표시이름(From display name)으로 2차 판별** |

**규율**
- **교차 검증 없이 단일 필드로 매칭하지 않는다**
- **매칭 결과는 표본을 눈으로 검수한다.** 수십 건짜리 오매칭 계획이 "이름이 그럴듯해서" 통과할 뻔했다
- 새 진행 파일은 **선점 확인 후** 만든다: `grep -rn "파일명" *.py`
- 한 레코드 안에 **같은 대상을 가리키는 필드가 둘이면 반드시 대조한다.** 어긋나도 아무 에러가 안 난다

**절단 키로 접두 조회할 때는 유일할 때만 채택한다**
외부 SKU가 20자에서 잘리니 원본 키로는 못 찾고 접두로 찾게 된다. 한 브랜드 300건 중 42건이 앞 20자가 충돌했다. **후보가 2건 이상이면 매칭을 포기**하고 유사도 폴백으로 넘긴다. 오연결보다 미연결이 낫다.
연결률은 **고정 분모(등록분) 대비**로 잰다. 맵 총계는 다른 스크립트가 계속 추가해 분모가 자라므로, 총계 대비로 보면 진척이 없어 보인다.

**확장자·선언 MIME은 포맷의 증거가 아니다**
PNG 바이트를 `image/jpeg`로 선언해 올렸더니 업로드 400. 파일명과 선언은 사람이 붙인 라벨이고 ②를 만족하지 않는다. **매직 바이트로 포맷을 판정**하고, 상대가 받는 포맷으로 변환한 뒤 올린다.

**한 레코드의 두 필드가 어긋났을 때의 교정 절차**
1,928건 중 46건에서 키와 URL이 서로 다른 상품을 가리켰다. 발주 시 **다른 물건을 사게 되는 직접 사고 경로**다.
1. **별도 색인에 등록된 쪽을 정본**으로 삼는다 — 키가 SKU 색인에 있으면 키를 믿는다
2. 반대쪽(URL)을 정본에서 **재생성**한다
3. **등재 시점에 두 필드가 같은 대상인지 검증**을 건다. 사후 대조보다 싸다

**"다른 것이 같은 이름"의 반대 — 같은 것이 다른 이름을 얻었다**
`.job_seen`과 `.jobs_seen`이 따로 있었다. 복수형 `s` 하나로 **처리 이력이 두 파일에 쪼개졌다.** A가 기록한 걸 B가 몰라 다시 처리하고, B가 기록한 걸 A가 몰라 안 보냈다. 에러는 없다. 오타가 아니라 **별개 파일로 성립**해버린다.
- 상태 파일 경로는 **상수 한 곳에** 정의한다. 문자열 리터럴로 흩지 않는다
- **비슷한 이름이 둘 이상 보이면 그 자체가 신호다** — 단·복수, 언더스코어 유무, 축약형

표의 진행 파일명 행과 정확히 대칭이다. 저건 다른 것이 같은 이름, 이건 같은 것이 다른 이름. **둘 다 이름을 계약으로 안 잡아서** 생긴다.

## 점수 없는 이름 매칭은 돈이 걸린 판단에서 사고를 낸다

**증상 3연속**

1. 한글명으로 검색해 엉뚱한 제품을 지목 → 다른 물건이 도착
2. 변형(variant)끼리 오매칭 → 권장가 5배 차이
3. 유사도 폴백 0.80이 같은 계열 제품을 서로 매칭 → **10만 원대 상품에 90만 원대 목표가**

**오매칭 신호**
★ **동일한 목표값이 5건 이상 반복되면 오매칭이다.** 실제로 한 값이 15건 반복됐다.

**해법**
- 임계 **0.92 + 2순위와 0.04 격차**
- 완료 시 **중복 결과 경고**
- 자동 적용 차단 조건: **중복 5건↑ 또는 변동폭 200%↑**
- ID 우선, 이름은 **마지막 수단**

**주의 — 임계를 올리면 반대쪽이 터진다**
오매칭을 잡으려고 임계를 0.80→0.92로 올렸더니 **미매칭이 폭증**했다(3천 건 검사에 절반 이상이 "원가 미상"). 진짜 원인은 임계가 아니라 **직결 조회 경로가 아예 없었던 것**이었다. 색인을 통한 직결 경로가 유사도 매칭보다 먼저다.
★ 직결 색인 자체가 신규 등록분을 자동 반영하지 않으면, 직결 경로를 켜도 같은 결과가 난다. **경로를 바꾸기 전에 색인부터 갱신**한다.

**오연결보다 미연결이 낫다.** 미연결은 "모른다"지만 오연결은 **"틀린 걸 안다고 믿는" 상태**다.

**화면에 그대로 보이는 지표에 부분매칭을 쓰면 오값이 곧 오판이다**
배송 알림 봇이 원가를 이름 부분매칭으로 붙였더니 마진율 `-101%` 같은 값이 화면에 그대로 떴다. 마진율은 사람이 그 자리에서 판단하는 숫자라 **틀린 값이 곧 틀린 결정**이 된다.
- 원가는 **SKU 정확매칭으로만** 붙인다
- ★ **못 찾으면 빈칸이 맞다.** 근사값을 채우면 "틀린 걸 안다고 믿는" 상태를 화면에 만든다

## 한글/CJK 부분일치는 짧은 단어가 긴 단어를 삼킨다

**증상**
필터에 등록한 짧은 한글 토큰이 무관한 긴 단어를 삼킨다.
`마블` ⊂ `마블링` · `핑` ⊂ `쇼핑` · `코브라` ⊂ 완구 상품명.

**원인 (트레이드오프)**
- ASCII 토큰은 **단어경계 매칭**이 가능하다(`shopping`의 `ping`, `dislodge`의 `lodge` 오탐 소멸)
- 한글/CJK는 공백 없는 연접이 흔해(`몽클레르패딩`) 단어경계를 쓰면 **미탐**이 난다 → 부분일치를 유지 → **짧은 한글이 긴 단어를 삼키는 과탐**이 생긴다

**해법 (예외 방식)**
경계 규칙을 바꾸지 않고 **정탐 보호 예외**를 둔다: term의 **모든 출현이 예외 단어 span 안에 갇히면 무시**, 예외 밖에도 있으면 진짜 히트. 연접 정탐(`몽클레르패딩`)은 그대로 살아남는다.
예외 추가는 목록에 한 줄이면 되고, 매칭 규칙 자체는 건드리지 않는다.

**첫 매치 우선 규칙표에서는 일반 패턴이 복합어를 삼킨다**
영문 상품명에서 품목을 뽑아 한글 종류어를 붙이는 규칙표를 돌렸다. `pen → 만년필`이 `Tactical Pen`을 먹어 택티컬펜이 만년필이 됐고, `mount → 거치대`가 `Rail-mounted`를 먹어 레일 장착형 제품이 거치대가 됐다. 같은 삼킴이 방향만 다르다 — 위는 짧은 토큰이 긴 단어를, 여기는 **일반 패턴이 복합어를** 삼킨다.
★ **구체적 패턴을 일반 패턴 앞에 둔다.** 첫 매치가 이기는 표에서는 순서가 곧 우선순위다. 표에 항목을 추가할 때 "이 패턴이 삼키는 기존 항목이 있나"를 먼저 본다.

## upsert가 워크플로 상태를 되돌린다

**증상**
"분명 처리 완료로 마킹했는데 목록에 다시 보인다."

**원인**
수집기가 만드는 레코드에 `'status': 'new'`가 박혀 있고, 6시간마다 도는 수집 크론의 `merge-duplicates` upsert가 **사람이 바꿔둔 상태를 전부 초기값으로 리셋**했다. 이미 발행한 항목이 재선택 대상으로 부활 — 하루만 늦었으면 중복 발행이 나갈 뻔했다.

**규칙**
- 수집기 레코드에서 **워크플로 상태 필드는 upsert 직전에 제거**한다 (`r.pop('status', None)`)
- **상태의 주인은 소비자지 수집기가 아니다.** 수집기는 사실만 쓴다

**증상 감지법**
"마킹했는데 다시 보인다" → 동기화 주기와 대조한다.

## 절단으로 값이 안 변하는 무한루프

**증상**
프로세스가 `Killed` (exit 137). **메모리 부족처럼 보인다.**

**원인**

```python
while cand in seen:
    cand = f"{cand} {i}"[:99]
```

이름이 **이미 99자면 절단 때문에 값이 안 변한다** → 영원히 돈다. 실측 메모리 사용량은 36MB였고 원인은 **CPU 무한루프**였다.

**해법**
- 루프 탈출 조건에 **카운터를 반드시 넣는다** (`_t < 20`)
- ★ 값을 증가시키는 연산 뒤에 **길이 제한이 붙으면 단조성이 깨진다.** 값이 변한다는 보장이 사라진다

접미를 붙여 유일화하는 **모든 코드**(SKU·파일명·아이템명)가 같은 형태다.

**검증**
`Killed`를 메모리 문제로 단정하지 말고 `ru_maxrss`로 실측한다.

## 공유 상태 파일에 소유자가 없으면 통째로 덮인다

**증상**
JSON 상태 파일 하나를 **3개 이상이 읽고 2개가 쓴다**(30분 크론 · 16분 크론 · 수동 배치). read-modify-write 사이에 다른 쓰기가 끼면 그 사이 변경분이 통째로 사라진다.

**해법 (세 개가 다 필요하다)**

1. `fcntl.flock`
2. **락을 잡은 뒤 재로드** — 락만으로는 부족하다. 락 획득 **전에** 읽은 값으로 쓰면 그 사이 변경분이 사라진다
3. `os.replace`로 원자적 교체

★ **진행 파일명 충돌과 같은 뿌리다: 공유 자원에 소유자가 없다.**

유실 0이었던 날도 있었지만 **순전히 운이었다.**

## 배포 대상의 파이썬 버전에 문법을 맞춘다

**증상**
로컬에서 잘 돌던 스크립트가 서버에서 `SyntaxError`로 죽는다. 런타임 에러가 아니라 **파싱 단계**라 한 줄도 실행되지 않는다.

**원인**
공유호스팅·구형 서버의 기본 파이썬이 **3.9**인 경우가 흔하다. 로컬은 3.11~3.12다.

| 문법 | 필요 버전 |
|---|---|
| `match` / `case` | 3.10+ |
| `X \| Y` 타입 힌트 | 3.10+ |
| `tomllib` | 3.11+ |
| `itertools.batched` | 3.12+ |

`urllib.request` · `os.path` · f-string은 안전하다.

**해법**
- 서버에서 `python3 -V`를 **먼저** 확인하고 그 버전 기준으로 쓴다
- ★ **한 프로젝트 안에서도 실행 위치마다 버전이 다를 수 있다** — PaaS 런타임과 SSH 서버가 다른 게 정상이다. **서버에서 도는 스크립트는 서버 기준으로** 쓴다
- CI가 있으면 최저 버전으로 한 번 파싱만 시켜도 잡힌다: `python3.9 -m py_compile *.py`

## 검증기가 잡아야 할 형태를 정상 목록에 넣어뒀다

**사고**
자동화가 **엉뚱한 값을 외부에 써 넣었다.** A 거래처의 주문번호가 B 주문의 운송장 번호로 들어갔고, **고객이 배송 추적을 못 하게 됐다.**

**1차 원인 — 매칭 키가 하나뿐**
매칭이 **거래처명 하나로만** 이뤄졌다. 같은 거래처에 건이 여럿이면 아무 데나 붙는다.

**2차 원인 — 이게 진짜다**
오류를 잡으라고 만들어둔 탐지 정규식에 **`^\d{10,14}$` 를 "정상 형식"으로 등록**해 두었다.
**그게 바로 이 사고의 형태였다.** 10자리 주문번호가 운송장 자리에 들어간 것.

★★ **검증기가 잡아야 할 결함의 서명을 화이트리스트에 올려놓고 있었다.**
"이건 정상 형식이니까"라고 넣은 규칙이 **정확히 그 사고를 통과시켰다.**

**★★ 되돌릴 수 없었다**
당시에는 **"수정 API가 없다"** 고 판단했다. 추측한 경로(`/invoices/correction`, `/invoices/update`)가 전부 404였기 때문이다.

**그 판단이 틀렸다.** 수정 경로는 있었고, 이름이 다를 뿐이었다 — 입력은 `.../invoices`, 수정은 `.../updateInvoices`. **같은 명사 아래 동사가 붙을 거라 가정**했는데 **별개 동사 경로**였다. 검색 한 번에 나왔고 전건 복구했다.

★★ **추측한 URL의 404는 "기능이 없다"가 아니라 "경로를 모른다"이다.** → 아래 별도 항목 참조

⚠️ **복구가 가능했다는 사실이 사고를 가볍게 만들지는 않는다.** 잘못된 값은 실제로 고객에게 보였고, 복구는 그걸 되돌린 게 아니라 **덮은 것**이다.

★ **비가역 쓰기는 사전 검증 말고는 방어 수단이 없다.** 사후 교정 경로가 있을 거라 가정하고 설계하면 안 된다.

**규율**

1. **검증기를 짤 때, 그 검증기가 잡아야 할 결함의 형태가 정상 목록에 있는지 본다**
2. ★ **탐지 규칙은 과거 사고 사례로 역검증한다.** 실제로 났던 오류를 넣어보고 **걸리는지 확인**한다. 안 걸리면 그 규칙은 없는 것과 같다
3. 외부에 쓰는 값은 **형식 검증 + 대상 매칭을 둘 다** 건다. 하나만으로는 부족하다

**곁가지 — 도달하지 않아 무사했던 결함**
이 결함은 **몇 주 전에 이미 기록돼 있었다.** 그때는 쓰기가 실제로 상대 시스템에 **도달하지 않아서** 피해가 없었고, 그래서 "확인됨" 정도로 남았다.
★★ **도달하지 않아서 무사했던 결함은 고쳐진 것이 아니다.** 경로가 열리는 날 그대로 터진다.

**최초 사고의 원인 넷 — 전부 "형태가 그럴듯한" 값이 통과한 것이다**

| 원인 | 처방 |
|---|---|
| 송장 정규식 `(\d{10,14})`가 **주문번호를 송장으로 오인** | 순수 숫자 패턴을 버리고 **캐리어 접두 패턴만** 채택 |
| `"getting your order ready to be shipped"`의 `shipped` 부분일치를 **발송으로 판정** | "준비중" 패턴을 따로 두고 주문접수/발송 분리 |
| keyword 빈 값이 필터를 **전부 통과**해 첫 주문에 무조건 기입 | keyword 없으면 중단 |
| 같은 거래처 주문이 2건 이상이면 **첫 건에 기입** | 모호하면 AMBIG 반환, 자동입력 중단 |

★ **처방이 노트에 적힌 것과 모든 호출 지점에 들어간 것은 별개다.** 재발 때 열어 보니 넷 중 ①과 ④가 그 경로에 없었다. 고친 함수가 아니라 **그 값을 쓰는 곳 전부**를 센다.

**거울상 — 정상 동작을 위반 지표로 넣으면 오탐 생성기가 된다**
위는 잡아야 할 결함을 정상 목록에 넣은 것이고, 이건 반대다. 표 셋의 정렬을 검사하는 도구에 "글자 시작 x 산포"를 위반 지표로 넣었더니 세 표 전부 "정렬 깨짐"으로 나왔다. 우정렬 금액 열은 오른쪽 끝이 모든 행에서 같은 값이었고, 시작점이 갈린 건 **자릿수 차이 그 자체**였다. 중앙정렬 열은 뱃지 폭이 다르면 양끝이 갈리는 게 **중앙정렬의 정의**다. 수리 후 재측정에서 값이 하나도 안 변한 것이 반증이었다 — 진범은 다른 열에 있었다.

| 정렬 | 맞아야 하는 것 | 갈려도 되는 것 |
|---|---|---|
| 좌정렬 | 시작(left) | 끝 |
| 우정렬 | **끝(right)** | **시작** |
| 중앙 | 중심 | 양끝 |

★ **지표를 고르기 전에 "이 숫자가 크면 뭐가 잘못된 건가"를 먼저 답한다.** 답이 없으면 그 숫자는 근거처럼 보이는 오독을 만든다 — 숫자가 붙어 있어서 근거 없는 추측보다 나쁘다.

## 실패 목록은 실패 기록이 아니라 "부재"로 구한다

**상황**
대량 등록 배치가 일일 한도에 걸려 **1,155건 중 333건이 거부**됐다. 어떤 것이 실패했는지 목록이 필요하다.

**틀린 방법 — 결과 CSV의 `FAIL` 파싱**
★ **CSV 컬럼 구조가 스크립트마다 다르다.** 배치를 여럿 굴리다 보면 열 순서·헤더 이름·구분자가 조금씩 갈리고, **파싱이 조용히 깨진다.** 그러면 실패 목록이 비거나 엉뚱해진다.

**맞는 방법 — 대상 시스템에 없는 것으로 역산**
보내려던 전체 목록에서 **"등록 완료 목록에 없는 것"** 을 뺀다.

★★ **실패 기록은 기록하는 쪽의 형식에 의존하지만, 부재는 대상 시스템의 사실이다.**

**왜 이게 일반적인가**
- 실패 기록은 **쓰기가 성공해야 남는다.** 프로세스가 중간에 죽으면 그 구간은 실패 기록조차 없다
- 부재는 **중간에 무슨 일이 있었든 상관없이** 성립한다
- ★ 같은 이유로 **"몇 건 성공"보다 "무엇이 아직 없는가"가 재실행 대상으로 안전하다**

**한도 자체에 대한 곁가지**
그 한도는 **상품 수가 아니라 옵션(variant) 수 기준**이었다. **옵션이 많은 상품은 훨씬 빨리 한도를 먹는다** — 같은 건수를 보내도 소진 속도가 다르다. ★ **한도의 단위가 내가 세는 단위와 같은지 먼저 확인한다.**

## 추측한 URL의 404는 "기능이 없다"가 아니다

**사고**
어떤 리소스를 수정하는 경로를 찾으면서 **이름을 추측해서** 두 개를 시도했다.

```
POST .../invoices/correction   → 404
POST .../invoices/update       → 404
```

여기서 **"이 플랫폼에는 수정 API가 없다. 비가역이다"** 라고 결론 냈다. 그 결론으로 **수동 복구 작업을 계획**하고, **문서에 "비가역"이라고 적었고**, 다른 사람에게도 그렇게 보고했다.

**틀렸다.** 검색 한 번에 실제 경로가 나왔다.

```
POST .../orders/updateInvoices
```

★ **입력은 `.../invoices`, 수정은 `.../updateInvoices`.**
**같은 명사 아래 동사가 붙을 것**이라고 가정했는데, 실제로는 **별개의 동사 경로**였다. 리소스 트리를 따르는 REST 관례를 상대가 지킬 거라고 믿은 게 전부였다.

**★★ 규칙**

1. **경로를 추측했다면 404는 근거가 아니다.** 판정 전에 **"이 URL을 내가 추측했나"** 를 먼저 자문한다
2. **"기능이 없다"는 문서·검색·문의를 거친 뒤에만** 말한다
3. ★ **"비가역"이라는 판정은 특히 비싸다.** 그 한 마디가 **수동 작업, 설계 변경, 사과**를 만든다. 비가역이라고 말하기 전에 **한 번 더 찾는다**

**★★★ 곁가지 — 이 규칙은 이미 적혀 있었다**

이틀 전, 다른 엔드포인트에서 404를 받고 **이렇게 기록해뒀다.**

> **404를 "그런 기능이 없다"로 읽지 않는다. 경로를 아직 못 찾은 것이다.**

**그리고 이틀 뒤에 그걸 어겼다.** 같은 주에 비슷한 일이 세 번 있었다 — 검증기가 자기가 잡을 결함을 통과시켰고, 형식 규칙을 정해놓고 그 규칙을 어겼고, 이번엔 **판정 규칙을 적어놓고 판정 순간에 꺼내지 않았다.**

★★ **규칙을 적는 것과 판정하는 순간에 그 규칙을 꺼내는 것은 별개의 능력이다.**
적어두는 것만으로는 안 되고, **판정 직전에 자동으로 걸리는 자리**(체크리스트·린트·리뷰 질문)에 넣어야 실제로 작동한다.

## 패턴 목록은 나열 순서가 곧 우선순위다

**증상**
문자열을 보고 종류를 판별하는 규칙을 여러 개 나열했다. **구체적인 케이스가 일반 규칙에 먹혔다.**

```
2-9-2 구조   → A        ← 일반 패턴이 앞
1Z로 시작    → B
LS로 시작    → C
```

`1Z...` 도 `LS...US` 도 앞의 일반 패턴에 먼저 걸려 **전부 A로 판별**된다. B와 C 규칙은 **한 번도 도달하지 않는다.**

**해법**

```
1Z · LS · 4PX  (구체적 접두)  ← 먼저
2-9-2 · 숫자 N자리 (일반 패턴)  ← 나중
```

★ **패턴 목록에서 나열 순서는 문서상의 순서가 아니라 실행 우선순위다. 순서를 설계로 취급한다.**

**두 번째로 겪었다**

같은 형태를 이전에도 밟았다 — 품목 분류 규칙에서 `Rail-mounted`의 `mount`가 '거치대'로, `Tactical Pen`의 `pen`이 '만년필'로 잡혔다. 짧고 일반적인 토큰이 앞에 있으면 **긴 구체적 토큰이 도달하지 못한다.**

★ **한 번 밟은 뒤에도 다른 도메인에서 같은 순서 실수를 반복했다.** 규칙 목록을 새로 쓸 때마다 **"구체적인 것이 위에 있나"** 를 확인한다.

## "통과했다"와 "맞다"는 다르다 — 폴백 값이 기능을 끄는 경우

**상황**
목록에 없는 값을 보내야 할 때, "무엇이든 받아주는" 범용 값이 있으면 그걸로 통과시키고 싶어진다.

**함정**
그 범용 값이 **기능을 끄는 값**일 수 있다. 이 경우 그 값은 **"추적 정보 없음"** 을 뜻했다 — 요청은 통과하지만 **최종 사용자에게는 추적 기능이 사라진다.** 게다가 그 상태에서는 **관리 화면에서 수정하는 것도 막힌다.**

★ **API가 받아준다는 사실이 그 값이 의미상 맞다는 뜻은 아니다.**
★ **폴백 값을 고를 때 "그 값이 켜는 것"이 아니라 "그 값이 끄는 것"을 본다.**

**대신 한 것**
목록에 없는 캐리어를 **송장 번호의 형식으로 판별해 가장 가까운 실제 코드에 매핑**했다. 추적이 살아 있는 쪽을 택했다.

## 파생 계산값과 원천 기록을 같은 자리에 두지 않는다

**증상**
원가를 `외화가 × 환율 × 계수`로 계산해 쓰고 있었다. 실제 결제 내역과 대조하니 **16% 차이**가 났다(추정 115,470 vs 실제 99,000).

**원인**
계수는 평균이고 환율은 시점이 다르다. **추정은 그 자체로는 틀린 게 아니지만, 원천 기록이 있는데도 추정을 쓰고 있었다.** 결제 확인 메일에 실제 금액이 있었다.

**해법**
- **실측값 전용 필드를 따로 만든다.** 있으면 무조건 우선
- ★ **추정치는 원천이 없을 때의 대체물이지 동급이 아니다.** 같은 필드에 섞으면 어느 쪽인지 알 수 없게 된다
- 추정으로만 판정된 건은 **별도 표시**한다. 16%는 **흑자와 적자를 뒤집는 폭**이다

★★ **추정 파이프라인이 길수록 입력 하나가 틀렸을 때 조용히 어긋난다.** 이 계산은 입력이 셋(외화가·환율·계수)이고, 그중 **통화 자체가 틀렸던 적**도 있었다.
## 배송지를 뽑았는데 청구지 우편번호가 섞여 나온다

**증상**
주문 메일에서 배송지를 추출해 "자사 주소면 본인 구매로 제외" 규칙을 걸었다. 실제 배송지는 다른 도시인데 **자사 주소 우편번호가 배송지에서 검출돼** 매칭이 거부됐다.

**원인**
메일 본문에서 `Shipping address` 헤더 뒤로 **고정 길이 300자**를 잘라 배송지로 썼다. 그 메일 형식은 배송지 바로 뒤에 `Billing address` 블록이 붙는다. 배송지가 짧으면 300자 안에 **청구지가 통째로 딸려 들어온다.** 청구지가 자사 주소였으니 규칙은 틀린 구간 위에서 정확히 동작한 셈이고, 에러는 없다.

**해법**
구간은 **다음 헤더 위치에서 끊는다.** 시작 마커에서 다음 마커(`Billing address`, 없으면 다음 빈 줄이나 섹션 헤더)까지. 고정 길이 절단 금지.

```python
start = body.index("Shipping address")
end = body.find("Billing address", start)
ship = body[start:end if end != -1 else start + LIMIT]
```

**검증**
추출 결과에 **다음 블록의 헤더 문자열이 들어 있으면 실패**로 본다. 배송지 안에 `Billing`이 있으면 절단이 틀린 것이다.

★ **구간 추출은 시작점만 잡으면 안 된다. 끝점도 잡아야 한다.** 고정 길이는 "다음 블록이 그 안에 안 들어온다"는 근거 없는 가정이다.

## `can't adapt type 'UUID'` — uuid 파라미터를 넘기면 500

**증상**

```
psycopg2.ProgrammingError: can't adapt type 'UUID'
```

`uuid.UUID` 값이나 `uuid[]` 리스트를 파라미터로 넘긴 INSERT/SELECT가 죽고, 그 위의 엔드포인트가 500을 낸다. 같은 쿼리가 SQL 클라이언트에서는 잘 돈다.

**원인**
psycopg2는 `uuid.UUID`를 **기본으로 어댑트하지 않는다.** 문자열로 넘길 때는 되고, UUID 객체를 넘기는 순간 터진다. 배열이면 원소마다 같은 문제다.

**해법**
임포트 직후 **한 번** 등록한다.

```python
import psycopg2.extras
psycopg2.extras.register_uuid()
```

프로세스당 한 번이면 된다. 커넥션마다 부르면 무해하지만 의미 없다.

**검증**
쿼리를 실제로 보내기 전에 `mogrify`로 바인딩 결과를 찍는다.

```python
cur.mogrify("SELECT %s, %s", (uuid.uuid4(), [uuid.uuid4()]))
# b"SELECT '...'::uuid, ARRAY['...'::uuid]"   ← 이 꼴이면 등록된 것
```

★ **어댑터 등록은 임포트 직후 한 곳에서.** 어떤 모듈에서는 되고 어떤 모듈에서는 안 되는 500은 등록 위치가 흩어져 있다는 뜻이다.

## 원가가 10~100배 부풀어 한 스토어 상품이 전부 적자로 집계된다

**증상**
소싱처 카탈로그 API의 `price`를 그대로 원가로 넣었더니 특정 스토어 상품들이 **전부 적자.** 마진 검사·재가격·소싱 판정이 한꺼번에 무효가 됐다.

**원인**
카탈로그 API의 `price`는 **그 스토어의 표시 통화**다. USD가 아니다. 스웨덴 브랜드는 SEK(×133원), 대만 브랜드는 TWD(×44.5원), 일본 브랜드는 JPY(×9.3원). 응답 어디에도 통화가 안 찍혀 있으니 `1400.00`이 USD 1,400인지 SEK 1,400인지 숫자만으로는 모른다.

**내가 한 오판**
숫자가 큰 걸 보고 **"센트 단위"라고 진단**해 한 스토어 65건을 `/100` 했다가 복구했다. 그 스토어는 정상 USD였다 — **멀쩡한 걸 망가뜨린 것이다.**
**가설 두 개(센트 단위 / 다른 통화)가 같은 숫자를 만든다.** 숫자만 보면 구분이 안 된다.

**해법 — 판별 순서**
1. **상품 페이지의 표시가와 API `price`를 대조한다.** 이게 확정 근거다
2. 브랜드 국적으로 통화를 먼저 추정한다 — 스웨덴이면 SEK부터 의심
3. 도메인 TLD도 단서지만 **단독으로는 부족**하다(`.com`인 유럽 브랜드가 많다)

교정 대상은 두 통화 939건 + JPY 14건이었다.

**검증**
변환 후 원가/판매가 비율이 **스토어 단위로** 정상 범위에 드는지 본다. 한 스토어가 통째로 적자거나 통째로 90% 마진이면 통화가 틀린 것이다.

★ **비가역 일괄 변환 전에 판별을 먼저 한다.** 값이 있다고 그 값의 단위가 맞는 게 아니다.

## `text-align: right`가 계산값에는 찍히는데 버튼 좌표는 안 움직인다

**증상**
표 액션 셀의 버튼 뭉치가 행마다 82px씩 어긋났다. 셀에 `text-align: right`를 걸고 `getComputedStyle`로 확인하니 `right`가 나온다. 그런데 버튼 좌표는 **하나도 안 변했다.**

```
셀 계산값: text-align: right                                  ← 먹은 것처럼 보인다
버튼 x:    행0 [1475, 1558, 1674] · 행1 [1393, 1518, 1634]     ← 그대로
```

**원인**
셀의 자식이 `<div class="d-flex ...">`였다. `text-align`은 **인라인 콘텐츠**의 배치 규칙이고, flex 컨테이너 안의 배치는 `justify-content`가 정한다. `text-align`은 **상속은 되고 적용은 안 된다.** `getComputedStyle`은 상속된 값을 정직하게 돌려주지만, 그 값을 쓰는 레이아웃 알고리즘이 아닐 뿐이다. 검사가 **엉뚱한 층**을 봤다.

**해법**
flex 자식에 `justify-content: flex-end`. 주자 버튼 오른쪽 끝이 `1892` 한 값으로 수렴했다.
구조를 모르면 **둘 다 건다** — flex/grid에는 `justify-content`/`align-items`, 인라인 흐름에는 `text-align`. 서로를 덮지 않는다.

**검증**
정렬 수리는 **좌표로 검증한다.** `getBoundingClientRect`로 버튼 x·오른쪽 끝·열 경계를 재서 행마다 같은 값으로 수렴하는지 본다. 계산값 검사는 "선언이 도달했나"만 본다. "그 선언이 무언가를 했나"는 좌표만 말해 준다.

★ **계산값은 필요조건이지 충분조건이 아니다.** 검사한 자리와 일하는 자리가 다르면 계산값도 초록도 거짓말을 한다.

## 값이 있다고 그 필드의 값인 건 아니다

**증상**
구조화 메타데이터(json-ld)의 `description`을 상품 설명으로 긁어왔다. 스키마상 위치도 맞고 타입도 문자열이라 **어떤 검증에도 안 걸린다.** 실제 내용은 이랬다.

```
"Used to get facts about the stores policies..."
```

**챗봇용 안내문**이었다.

**★★ 판별법 — 두 건을 나란히 놓는다**
★ **두 레코드가 같은 문자열이면 그건 개별 값이 아니라 사이트 공통 문구다.**
**한 건만 보면 그럴듯하다.** 정체는 비교에서만 드러난다.

같은 형태를 다른 자리에서도 겪었다 — 생성된 본문이 **여러 건에서 정확히 같은 길이**로 나왔고, 그게 자기 산출물을 다시 읽고 있다는 신호였다.

★ **출력이 여러 건에서 동일하면 그 자체가 신호다.** 스키마 검증은 이걸 절대 못 잡는다.

**곁가지 — 막힌 축을 뚫는 대신 다른 축으로**
본문 확보는 도메인마다 다른 이유로 막혔다(JS 렌더링 / 라우팅 부재 / 공통 문구). 하나씩 뚫는 대신 **본문이 필요 없는 구성**으로 갔다 — 이미지가 충분하면 텍스트가 짧아도 성립하는 채널이었다.
★ **막힌 것을 뚫는 것과 필요 없게 만드는 것은 다른 수단이다.** 후자가 싼 경우가 많다.

## 같은 자료구조가 두 의미를 담으면 반드시 오독된다

**상황**
한 레코드의 `sources` 배열에 항목이 여러 개 있었다. 1,107건이 그랬다.

새 기능(묶음 상품)을 설계하면서 **"여러 개니까 이게 묶음이겠네"** 로 읽을 뻔했다. 실제로는 **대체 공급처 목록**이었다.

★★ **그렇게 읽었으면 1,107건에 잘못된 발주가 나갔다.**

**해법 — 형태가 아니라 의미로 필드를 나눈다**

```json
{"is_set": true,
 "set_items": [...],   // 묶음 구성품
 "sources":   [...]}   // 대체 공급처
```

둘 다 배열이지만 **이름이 다르고, 소비하는 코드가 다르다.** 플래그가 켜져 있고 전용 필드가 있을 때만 묶음으로 처리한다.

★ **"여러 개"라는 형태가 같다고 의미가 같은 게 아니다.**
★★ **쓰지 않을 기능의 구조를 미리 넣은 이유** — 나중에 넣으면 **기존 1,107건을 재해석해야 하고, 그 순간 혼동이 난다.** 구분은 값이 적을 때 박아둔다.

## 역산의 기준이 낡았으면 역산도 틀린다

앞에서 **"실패 목록은 실패 기록이 아니라 부재로 구한다"** 고 썼다. 그건 맞다. **그런데 순서가 하나 더 있다.**

**증상**
부재로 역산했더니 미처리가 **1,371건**으로 나왔다. 실제로는 **170건**이었다.

**원인**
대조 기준으로 쓴 "완료 목록"이 **갱신 전 스냅샷**이었다. **방금 처리한 것들이 전부 미처리로 집계**됐다.

★★ **부재로 역산하는 방법은 "기준이 현재 상태"임을 전제한다.**
기준을 먼저 갱신하지 않으면 **방금 한 일이 안 한 일이 된다.**

**순서**
```
1. 기준 목록을 갱신한다   ← 빠뜨리기 쉬운 단계
2. 보내려던 전체와 대조한다
3. 없는 것이 미처리다
```

★ 재실행 대상을 8배로 부풀린 채 배치를 돌리면, **이미 끝난 일을 다시 하면서 한도까지 먹는다.**

## `400`의 사유는 예외 객체가 들고 있다

**증상**
메시지 발송 API가 `400 Bad Request`. 본문 형식을 의심해 이스케이프·길이·특수문자를 계속 만졌다. 전부 헛수고였다.

**원인**
응답 본문에 사유가 있었다.

```
{"description": "Bad Request: PEER_FLOOD"}
```

**짧은 시간 과다 발송에 대한 발신자 단위 제한**이었다. 내용과 무관하다. `HTTPError`를 잡고 **상태코드만 꺼낸 뒤 본문을 버리고 있었다.**

★★ **예외 객체는 응답을 들고 있다.** `e.read()` 한 줄이면 나온다. 상태코드만 보면 **사유가 통째로 사라진다.**

**판별 — 같은 입력을 다른 발신자로**
같은 본문을 **다른 발신자로 보내니 성공**했다. 그게 "내용 문제가 아니다"의 증거다.
★ **한 변인만 바꿔 재현해보면 내용 문제와 상태 문제가 갈린다.**

**대응 — 3단계**
1. 발송 성공 후 **고정 간격 대기**
2. 제한 감지 시 **더 긴 대기 후 재시도**
3. 그래도 실패하면 **다른 발신자로 대체 발송**

★ 채널을 **성격별로 나눠뒀던 것이 여기서 가용성 이중화가 됐다.** 분리는 그 자체로 대체 경로를 만든다 — 발신자가 하나였으면 3단계가 없다.

**★★ 곁가지 — 테스트가 운영 쿼터를 소모한다**
이 제한에 걸린 계기는 **테스트였다.** 멱등성 파일(이미 처리한 목록)을 반복해서 비우며 돌렸더니, **같은 알림을 몇 번이고 다시 보내게 됐다.**

★★ **외부 쿼터를 쓰는 대상을 테스트할 때, "처리 기록을 비우고 다시 돌린다"는 방식은 발송량을 곱한다.** 테스트가 운영을 망가뜨리는 경로다. 쿼터를 쓰지 않는 더미 수신자를 따로 둔다.

## 한 축만 풀면 다른 축이 병목이 된다

**상황**
판매 가능 수량이 근거 없이 **일괄 3**으로 박혀 있었다. 3개 팔리면 품절이 되고, 품절은 노출을 끊는다. **스스로 노출을 막고 있었다.**

★ **"일단 3"으로 시작한 값이 아무도 다시 안 보는 사이 천장이 됐다.** 임시값에 근거가 없으면 재검토 시점도 없다.

**수량을 올렸는데도 안 풀리는 이유**
같은 리소스에 **1회 구매 수량 한도**가 별도로 있었고, 그것도 3이었다.

★★ **두 상한이 걸린 자원에서 실제 처리량은 둘 중 작은 쪽으로 정해진다.** 한쪽만 올리면 아무것도 안 바뀐다.

**점검 습관**
- 상한을 올릴 때 **같은 흐름에 걸린 다른 상한을 전부 나열**한다
- ★ 한도가 여럿이면 **어느 단위로 세는지도 각각 다르다** — 하나는 총량, 하나는 1회당일 수 있다
- 임시값을 넣을 땐 **재검토 조건을 같이 적는다.** 조건이 없으면 영구값이 된다

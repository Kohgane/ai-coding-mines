# Python · DB · 데이터 로직

이 장의 절반은 **"조용한 실패"** 한 가지 형태다. 실패가 성공처럼, 또는 사실처럼 보이는 구조.

---

## 조용한 실패 — 실패가 성공처럼 보이는 구조 (총론)

예외가 안 나고 로그도 안 남는다. 하루에 다섯 건이 이 형태였던 날도 있었다.

| 액면 신호 | 실제 |
|---|---|
| CI 그린 | 실동작 아님 |
| 검색 결과 0건 | 봇 차단 페이지(2KB) |
| 진행 파일에 `ok:225` | 자기가 만든 껍데기를 다시 읽었다 |
| `PUT 200 SUCCESS` | 값이 안 바뀜. 6주간 무효 |
| 함수가 "전건 미발견" | 튜플을 문자열처럼 다뤘다 |
| 크론이 정상 종료(0) | 가드가 자기를 잡아 한 번도 안 돌았다 |
| `registered: true, reason: null` | 이미지 0장 |
| 문서의 "전량 삭제 완료" | 68건 잔존 |

**원칙 — 판정 전에 원자료를 본다**
- 0건·미발견·성공플래그는 **결론이 아니라 관측**이다. 그 관측이 나온 경위를 먼저 본다
- 요약·상태 문구가 아니라 **원본 필드**를 읽는다
- "완료"라고 찍혔는지가 아니라 **몇 개가 나왔는지** 센다
- **응답 크기·타입을 검사한다.** `len < 임계`거나 예상 타입과 다르면 실패로 간주한다

## "없음"과 "못 찾음"은 다른 사실이다

**증상**
조회 결과 0건. 여기서 갈라지는 두 해석이 **정반대 결론**을 만든다.

| 관측 | 해석 A (없음) | 해석 B (실패) |
|---|---|---|
| 검색 0건 | 그 대상이 없음 | **무작위 봇 차단** |
| 메일 0건 | 새 메일 없음 | **SINCE·LIMIT 필터에 걸림** |
| 카탈로그에서 항목 미발견 | 단종 | **페이지를 덜 긁음** |
| 배치 처리 0건 | 대상 없음 | **대상 목록의 소스가 다름** |
| 텍스트 0자 | 본문 없음 | **본문이 이미지 태그뿐** |
| `products.json` 404 | 카탈로그 없음 | **그 플랫폼이 아닐 뿐** |
| 도메인 미발견 | 사이트 없음 | **추측으로 두드렸을 뿐** |

**판별법**
- **응답 크기를 본다.** 정상 응답이 2KB일 수 없는 자리에서 2KB가 오면 실패다
- **조건을 하나씩 푼다.** 기간·건수·상태·타입을 넓혀 **0이 유지되는지** 본다
- **다른 경로로 교차 확인한다**
- **모수를 함께 센다.** `0/N`에서 **N을 모르면 0의 의미도 모른다**

**대가**
이 구분을 안 해서 사흘간 치른 값: 4개 로케일 "재고 없음" 오판 · 메일 12건을 0건으로 판정(3회 반복) · 배치 대상 0건 · "단종" 판정(실제로는 도메인이 달랐다).

## 반환 스키마를 가정하면 조용히 헛돈다

**증상**
`h = get(...)` 로 받아 `in`·정규식·길이 검사를 걸었는데 **전건 미발견**으로 나온다. 예외는 안 난다.

**원인**
`get()`이 `(status, body)` **튜플**을 돌려주고 있었다. 튜플에 `in`을 걸면 원소 동등성 검사가 되어 항상 False, `len()`은 2가 된다. 문법적으로 전부 유효해서 아무도 안 죽는다.

**해법**
`status, body = get(...)` 로 언패킹. 그리고 **반환 스키마를 가정하지 말고 한 번 찍어보고 쓴다.**

**검증**

```python
print(type(r), repr(r)[:200])
```

진행 파일·집계 대상도 마찬가지다. `list(d.items())[:3]`으로 값 스키마를 먼저 본다. 스키마를 가정하고 돌린 집계는 0을 내놓고, **0은 "데이터 없음"으로 오독된다.**

## 진행 파일에 결과를 안 남기면 사후 검증이 불가능해진다

**증상**
`*_done.json`이 `{id: true}`만 기록해 **무엇을 썼는지 남지 않는다.** 나중에 불량이 발견됐을 때 완료 2천여 건 중 몇 건이 불량인지 로컬에서 셀 수 없다.

**해법**
done 파일에 최소 3필드: `{id: {ts, len, src}}` — 생성 본문 길이와 원본 출처만 있으면 사후 전수 검증이 로컬에서 끝난다.

**★★ 접두 형식을 쓰면 판정 연산자가 바뀐다**

값에 사유를 남기려고 접두 형식을 쓰는 건 좋다 — 무엇을 왜 그렇게 처리했는지가 남는다.

```
done[x] = "ok:16371818883" / "skip:정책제외" / "manual:검토필요" / "fail2"
```

**그러면 판정은 반드시 `startswith`여야 한다.**

```python
done_ok = str(v).startswith(("ok", "skip", "manual"))
```

★ **`!= "ok"` 나 `not in ("ok", "skip")` 은 접두 형식에서 항상 통과한다.**
`"ok:16371818883" != "ok"` 는 **True**다 → **완료된 건을 매 회차 재처리한다.** 에러는 없고, 로그는 정상이고, **목록만 영원히 안 비운다.**

**더 안전한 형태 — 판정 대상과 설명을 분리한다**

```python
done[x] = {"state": "ok", "detail": "16371818883"}
```

값 하나에 두 정보를 담으면 **읽는 쪽이 매번 파싱 규약을 지켜야 하고, 한 곳만 틀려도 샌다.**

**같은 연산자 위험의 반대 방향**

| 값 체계 | 틀린 연산자 | 결과 |
|---|---|---|
| `"ok:123"` | `!= "ok"` | 완료를 미완료로 읽어 **무한 재처리** |
| `임시저장` / `임시저장중` | `== "임시저장"` | 해당 건을 **누락** |

★ **접두어를 공유하는 값 체계에서는 `==`도 `!=`도 둘 다 위험하다.** 한쪽은 빠뜨리고 한쪽은 다 통과시킨다.
★ **값 형식을 정할 때 판정 코드를 같이 정한다.** 나중에 형식만 바꾸면 판정이 조용히 뒤집힌다.

**★★ `continue` 전에 저장하지 않으면 판단이 사라진다**

루프 안에서 **상태를 메모리에만 바꾸고 `continue`** 하면, 그 회차가 죽거나 다음 저장 전에 끊겼을 때 **판단한 사실 자체가 없어진다.** 다음 회차가 같은 건을 처음 보는 것처럼 다시 처리한다.

★ **상태를 바꾸면 그 자리에서 저장한다. 루프 끝 저장만 믿지 않는다.**

이건 "실패도 기록해야 한다"와 **한 겹 다르다** — 저기는 **기록할 생각을 안 한 것**이고, 여기는 **기록했는데 안 쓰인 것**이다.

**★★ 네 형태가 전부 같은 증상을 낸다**

같은 진행 파일 하나를 두고 네 가지 방식으로 틀렸다. **하루에 넷 다 밟았다.**

| | 형태 | 증상 |
|---|---|---|
| ① | 값 형식을 바꾸고 판정부를 안 고침 | `"ok:123" != "ok"` 통과 → 완료를 재처리 |
| ② | `==` 로 판정 | 접두어를 공유하는 값을 누락 |
| ③ | 응답만 보고 `ok` | 재조회 검증 없음 → **완료 기록이 통째로 허수** |
| ④ | `continue` 전에 저장 안 함 | 판단이 사라져 **무한 재처리** |

★ **넷 다 에러가 없고, 넷 다 목록이 안 빈다.**
그래서 **하나를 고쳐도 증상이 남으면 "안 고쳐졌다"가 아니라 "다른 형태가 또 있다"로 읽어야 한다.**

**규약 — 셋 다 필요하다**

1. **판정은 `startswith`** — 접두 형식이면 `==`·`!=` 둘 다 위험하다
2. **저장은 즉시** — 상태를 바꾸면 그 자리에서
3. **완료는 재조회로 확인** — 응답은 증거가 아니다

★ **셋 중 하나만 빠져도 목록은 안 빈다. 그리고 어느 게 빠졌는지는 증상으로 구분되지 않는다.**

**같이 밟는 것 — "처리 못 함"과 "처리 필요 없음"의 혼동**
실패를 `done`에 안 남기면 **무한 재시도 루프**가 된다. 반대로 "이미 처리할 필요가 없어진 건"을 미처리로 분류하면 목록이 영원히 안 비고 배치가 20분마다 같은 일을 반복한다(로그만 385KB 쌓였다).
→ **실패도 기록하되, 두 상태를 구분해 기록한다.**

## 폴백 체인에서 앞단이 `continue`하면 뒷단이 전부 죽는다

**증상**
폴백을 4단 쌓았는데 100여 건이 "원본 없음"으로 기록됐다. 실제로는 회복 가능한 건이었다.

**원인**
1단(웹검색) 실패 시 `done[id]="nourl"; continue` — 그 아래 2·3·4단이 **한 번도 실행되지 않았다.**

**핵심**
진행 파일의 실패 사유는 **어느 단계에서 나갔는지**를 말할 뿐, "모든 수단을 다 썼다"를 뜻하지 않는다. 실패 코드를 근거로 처방을 정하기 전에 **그 코드가 찍히는 지점이 체인의 어디인지** 확인한다.

## 성공 응답에 "핵심 산출물 0개"가 섞이면 성공이 아니다

**증상**
등록 47/47이 `registered: true`, `reason: null`로 전부 성공. 그런데 **전량 이미지 0장**이었다. 실물을 눈으로 볼 때까지 아무도 몰랐다.

**원인**
외부 데이터의 형식을 가정했다. 엔트리가 `{name, sources:[{url, priority}...]}` 구조인데 `v.get("url")`로 flatten해서 전부 `None`이 됐다. URL이 빈 문자열이 되니 수집이 아예 안 돌았고, 그래도 등록 자체는 성공했다.

**해법**
- 성공 + `image_count == 0`이면 `warning` + 상단 집계로 **표면화**한다
- 외부 데이터 **형식 가정 금지** — 실제 1건 열어보고 키를 확인한다

**규율**
수집=이미지, 등록=이미지, 번역=번역본 — **"있어야 할 것 0개"는 조용히 넘기지 않는다.**

## "완료" 기록이 완료를 뜻하지 않는다

**증상**
천여 건이 `ok`로 기록됐는데 표본 40건이 전부 원본 그대로였다. `ok`의 근거는 `status_code == 200` 하나였다.

**해법**
완료를 적을 때 **무엇으로 검증했는지 같이 적는다** — `재조회 N건` / `전수 재조회` / `미검증`.
검증 안 한 완료는 **"실행함"이라고만 적는다.**

성공 판정을 함수로 강제한다.

```python
def ok(code, resp):
    return code == 200 and isinstance(resp, dict) and resp.get("code") != "ERROR"
```

이걸 안 넣어 700여 건을 헛돌렸다. 전부 거부됐는데 진행 파일에는 `put`으로 기록됐다.

## 저장된 판정값을 화면이 그대로 믿으면 옛 상태가 산다

**증상**
데이터를 고쳤는데 화면에 옛 판정(실패 뱃지, 옛 카운트)이 그대로 남는다.

**해법**
**조회 시 재계산.** 저장값은 캐시일 뿐 신뢰의 원천이 아니다. 목록과 상세 **양쪽 모두** 재계산한다.

## 가공된 표시본을 다시 처리하면 오염이 잔존한다

**증상**
이미 번역된 제목을 재번역하니 상용구 제거 로직이 무력화돼 찌꺼기가 남는다.

**해법**
재번역·재계산은 **항상 원본에서** 시작한다(`title_en`이지 `title_ko`가 아니다).

**함정**
소스 폴백에 `_ko` 필드가 숨어 있는 경우가 많다. `description or description_ko` — 원본이 없으면 표시 번역본을 다시 번역한다(한글→한글). 한 필드를 고쳐도 **형제 필드의 소스 폴백에 표시본이 남았는지 전수 확인**한다.

## 같은 값을 두 경로가 각자 계산하면 갈라진다

**증상**
"화면엔 맞게 나오는데 전송/저장만 0 또는 빈값."

**원인**
검수 화면(GET)과 실제 전송(POST)이 **각자** 같은 빌더 함수를 호출했다. 한쪽만 환율 파라미터를 주입해서, GET은 수십만 원대 가격을 표시하고 POST는 `None` → `int(None or 0)` → **0을 전송**했다.

**판별**
- 같은 도메인 값(가격·분류·키)을 **두 군데 이상에서 만들고 있나?**
- 두 호출부의 **인자 목록 차이**가 곧 갈라짐의 크기다

**처방**
1. **단일 소스 헬퍼**로 묶는다
2. 파생값은 **한 번 계산해 넘긴다**
3. **미확정을 0으로 강등하지 마라.** `int(x or 0)`은 "모름"을 "0"으로 둔갑시켜 조용히 전송한다
4. 계약 테스트로 **표시값 == 전송값**을 못 박는다. 양쪽을 따로 검증하면 갈라짐을 못 잡는다

## 배치 진행률을 전체 비율로 읽으면 안 된다

**증상**
배치를 돌리며 로그를 보니 실패가 **8건뿐**이었다. "거의 다 됐다"고 판단했다.

**원인**
그건 **배치 앞 구간만 돈 결과**였다. 구간을 건너뛰며 다시 재보니 분포가 전혀 달랐다.

| offset | 성공률 |
|---|---|
| 0~4,000 | **92~95%** |
| 6,000 | **44%** |
| 8,000 | **0%** |
| 9,400 | **84%** |

**전체는 68.3%였다.**

★★ **정렬 순서가 편향을 만든다.** 등록순으로 정렬하면 **앞 구간은 최신 데이터라 잘 정비돼 있다.** 앞만 보고 전체를 추정하면 항상 낙관 쪽으로 틀린다.

**해법**
- **offset을 건너뛰며 표본을 뽑는다.** 앞에서 N건이 아니라 **구간마다 N건**
- 진행률 로그에 **어디까지 처리했는지**를 같이 찍는다. `"실패 8건"`만으로는 모수를 모른다
- ★ **0%인 구간이 있는지 본다.** 평균은 그런 구간을 숨긴다

같은 형태를 표본 크기에서도 겪었다. 같은 조사를 세 번 했는데 **세 번 다 같은 방향으로 틀렸다.**

| 표본 | 불량률 |
|---|---|
| 500 | 36% |
| 1,900 | 48% |
| 4,900 | **69%** |

★★ **추정이 계속 한 방향으로만 갱신되면, 그건 아직 수렴하지 않았다는 뜻이다.**
표본을 키울 때마다 나빠지고 한 번도 반대로 안 갔다면, **지금 값도 아직 하한이다.**
**작은 표본과 앞쪽 표본은 둘 다 낙관 쪽으로 틀린다.**

**실제**
원가를 못 구한 **31.7%가 미연결 집합과 정확히 같았다.** 계산식을 고치거나 매칭 임계를 조정해도 안 움직이는 게 당연했다 — **계산할 원본이 없었다.**

★ **지표 이름이 다르다고 대상이 다른 게 아니다.** 두 목록의 **교집합을 한 번 세보면** 끝난다.
★ 이건 [식별자 오용](#식별자를-쓰기-전에-두-가지를-확인한다)의 지표 판이다 — **같은 대상을 가리키는 것이 둘이면 대조한다.**

## 키 정규화는 양방향을 다 봐야 한다

같은 대상을 가리키는 키가 어긋나는 방식이 **두 방향**이다. 한쪽만 고치면 반대쪽이 그대로 남는다.

| 방향 | 원인 | 증상 |
|---|---|---|
| **다른 것 → 같은 키** | 절단으로 접미가 잘려나감 | 덮어써서 **마지막 것만 남는다** |
| **같은 것 → 다른 키** | 재등록 때마다 **접미가 붙는다** | 조회가 **아예 안 붙는다** |

**두 번째 방향의 실제 모습**

```
B0734ZHGXK → B0734ZHGXKAB → ...R / RR / RRR
```

재등록·재생성 때마다 접미가 하나씩 붙는다. 사람이 보면 같은 물건인데 키로는 완전히 다르다.

**해법**
1. **접미·접두를 전개해 후보를 만든다** — 원본 / 접미 제거 / 접두 제거
2. **소문자·특수문자 제거 인덱스**로 **교차 조회**한다

적용 후 8,858건 중 6,657건(75%)이 붙었다.

★ **전개로도 안 붙는 게 남는다** — 아예 다른 채번 체계로 만들어진 키다. **채번 시점에 대응 키를 같이 박지 않으면 사후 복구가 안 된다.** 생성과 등재를 같은 코드에서 처리한다.

## 식별자를 쓰기 전에 두 가지를 확인한다

**필드를 식별자로 쓰기 전:**

1. **유일한가** — 값이 겹치지 않는가
2. **식별용인가** — 그 필드가 **대상을 지목하려고 존재하는가**

**①만 보고 ②를 안 보면** 태그 같은 검색용 필드를 키로 쓴다.
**②만 보고 ①을 안 보면** 정식 식별자에 절단·부모공유로 당한다.

| 쓴 필드 | 깨진 조건 |
|---|---|
| 외부 SKU 필드 | **①** — 20자에서 절단 저장. 중복이 전체의 **40%대** |
| 상품 이름으로 인덱싱 | **①②** — 상태 파일이 섞여 본문 없는 껍데기가 선점 |
| 상품명 매칭 | **②** — 3연속 사고 |
| 플랫폼 `tags` | **②** — 검색용 롱테일. 태그 하나로 품목 오분류 |
| 진행 파일명 | **①** — 다른 스크립트가 **다른 형식으로 같은 이름** 사용 → 200여 건 유실 |
| 카테고리 **이름** | **②** — 부분일치 오탐. 리프 **ID**로 고정해 해결 |
| 한 레코드의 두 필드 | **①** — 키와 URL이 **서로 다른 대상**을 가리킴 |

**규율**
- **교차 검증 없이 단일 필드로 매칭하지 않는다**
- **매칭 결과는 표본을 눈으로 검수한다.** 수십 건짜리 오매칭 계획이 "이름이 그럴듯해서" 통과할 뻔했다
- 새 진행 파일은 **선점 확인 후** 만든다: `grep -rn "파일명" *.py`
- 한 레코드 안에 **같은 대상을 가리키는 필드가 둘이면 반드시 대조한다.** 어긋나도 아무 에러가 안 난다

## 점수 없는 이름 매칭은 돈이 걸린 판단에서 사고를 낸다

**증상 3연속**

1. 한글명으로 검색해 엉뚱한 제품을 지목 → 다른 물건이 도착
2. 변형(variant)끼리 오매칭 → 권장가 5배 차이
3. 유사도 폴백 0.80이 같은 계열 제품을 서로 매칭 → **10만 원대 상품에 90만 원대 목표가**

**오매칭 신호**
★ **동일한 목표값이 5건 이상 반복되면 오매칭이다.** 실제로 한 값이 15건 반복됐다.

**해법**
- 임계 **0.92 + 2순위와 0.04 격차**
- 완료 시 **중복 결과 경고**
- 자동 적용 차단 조건: **중복 5건↑ 또는 변동폭 200%↑**
- ID 우선, 이름은 **마지막 수단**

**주의 — 임계를 올리면 반대쪽이 터진다**
오매칭을 잡으려고 임계를 0.80→0.92로 올렸더니 **미매칭이 폭증**했다(3천 건 검사에 절반 이상이 "원가 미상"). 진짜 원인은 임계가 아니라 **직결 조회 경로가 아예 없었던 것**이었다. 색인을 통한 직결 경로가 유사도 매칭보다 먼저다.

**오연결보다 미연결이 낫다.** 미연결은 "모른다"지만 오연결은 **"틀린 걸 안다고 믿는" 상태**다.

## 한글/CJK 부분일치는 짧은 단어가 긴 단어를 삼킨다

**증상**
필터에 등록한 짧은 한글 토큰이 무관한 긴 단어를 삼킨다.
`마블` ⊂ `마블링` · `핑` ⊂ `쇼핑` · `코브라` ⊂ 완구 상품명.

**원인 (트레이드오프)**
- ASCII 토큰은 **단어경계 매칭**이 가능하다(`shopping`의 `ping`, `dislodge`의 `lodge` 오탐 소멸)
- 한글/CJK는 공백 없는 연접이 흔해(`몽클레르패딩`) 단어경계를 쓰면 **미탐**이 난다 → 부분일치를 유지 → **짧은 한글이 긴 단어를 삼키는 과탐**이 생긴다

**해법 (예외 방식)**
경계 규칙을 바꾸지 않고 **정탐 보호 예외**를 둔다: term의 **모든 출현이 예외 단어 span 안에 갇히면 무시**, 예외 밖에도 있으면 진짜 히트. 연접 정탐(`몽클레르패딩`)은 그대로 살아남는다.
예외 추가는 목록에 한 줄이면 되고, 매칭 규칙 자체는 건드리지 않는다.

## upsert가 워크플로 상태를 되돌린다

**증상**
"분명 처리 완료로 마킹했는데 목록에 다시 보인다."

**원인**
수집기가 만드는 레코드에 `'status': 'new'`가 박혀 있고, 6시간마다 도는 수집 크론의 `merge-duplicates` upsert가 **사람이 바꿔둔 상태를 전부 초기값으로 리셋**했다. 이미 발행한 항목이 재선택 대상으로 부활 — 하루만 늦었으면 중복 발행이 나갈 뻔했다.

**규칙**
- 수집기 레코드에서 **워크플로 상태 필드는 upsert 직전에 제거**한다 (`r.pop('status', None)`)
- **상태의 주인은 소비자지 수집기가 아니다.** 수집기는 사실만 쓴다

**증상 감지법**
"마킹했는데 다시 보인다" → 동기화 주기와 대조한다.

## 절단으로 값이 안 변하는 무한루프

**증상**
프로세스가 `Killed` (exit 137). **메모리 부족처럼 보인다.**

**원인**

```python
while cand in seen:
    cand = f"{cand} {i}"[:99]
```

이름이 **이미 99자면 절단 때문에 값이 안 변한다** → 영원히 돈다. 실측 메모리 사용량은 36MB였고 원인은 **CPU 무한루프**였다.

**해법**
- 루프 탈출 조건에 **카운터를 반드시 넣는다** (`_t < 20`)
- ★ 값을 증가시키는 연산 뒤에 **길이 제한이 붙으면 단조성이 깨진다.** 값이 변한다는 보장이 사라진다

접미를 붙여 유일화하는 **모든 코드**(SKU·파일명·아이템명)가 같은 형태다.

**검증**
`Killed`를 메모리 문제로 단정하지 말고 `ru_maxrss`로 실측한다.

## 공유 상태 파일에 소유자가 없으면 통째로 덮인다

**증상**
JSON 상태 파일 하나를 **3개 이상이 읽고 2개가 쓴다**(30분 크론 · 16분 크론 · 수동 배치). read-modify-write 사이에 다른 쓰기가 끼면 그 사이 변경분이 통째로 사라진다.

**해법 (세 개가 다 필요하다)**

1. `fcntl.flock`
2. **락을 잡은 뒤 재로드** — 락만으로는 부족하다. 락 획득 **전에** 읽은 값으로 쓰면 그 사이 변경분이 사라진다
3. `os.replace`로 원자적 교체

★ **진행 파일명 충돌과 같은 뿌리다: 공유 자원에 소유자가 없다.**

유실 0이었던 날도 있었지만 **순전히 운이었다.**

## 배포 대상의 파이썬 버전에 문법을 맞춘다

**증상**
로컬에서 잘 돌던 스크립트가 서버에서 `SyntaxError`로 죽는다. 런타임 에러가 아니라 **파싱 단계**라 한 줄도 실행되지 않는다.

**원인**
공유호스팅·구형 서버의 기본 파이썬이 **3.9**인 경우가 흔하다. 로컬은 3.11~3.12다.

| 문법 | 필요 버전 |
|---|---|
| `match` / `case` | 3.10+ |
| `X \| Y` 타입 힌트 | 3.10+ |
| `tomllib` | 3.11+ |
| `itertools.batched` | 3.12+ |

`urllib.request` · `os.path` · f-string은 안전하다.

**해법**
- 서버에서 `python3 -V`를 **먼저** 확인하고 그 버전 기준으로 쓴다
- ★ **한 프로젝트 안에서도 실행 위치마다 버전이 다를 수 있다** — PaaS 런타임과 SSH 서버가 다른 게 정상이다. **서버에서 도는 스크립트는 서버 기준으로** 쓴다
- CI가 있으면 최저 버전으로 한 번 파싱만 시켜도 잡힌다: `python3.9 -m py_compile *.py`

## 검증기가 잡아야 할 형태를 정상 목록에 넣어뒀다

**사고**
자동화가 **엉뚱한 값을 외부에 써 넣었다.** A 거래처의 주문번호가 B 주문의 운송장 번호로 들어갔고, **고객이 배송 추적을 못 하게 됐다.**

**1차 원인 — 매칭 키가 하나뿐**
매칭이 **거래처명 하나로만** 이뤄졌다. 같은 거래처에 건이 여럿이면 아무 데나 붙는다.

**2차 원인 — 이게 진짜다**
오류를 잡으라고 만들어둔 탐지 정규식에 **`^\d{10,14}$` 를 "정상 형식"으로 등록**해 두었다.
**그게 바로 이 사고의 형태였다.** 10자리 주문번호가 운송장 자리에 들어간 것.

★★ **검증기가 잡아야 할 결함의 서명을 화이트리스트에 올려놓고 있었다.**
"이건 정상 형식이니까"라고 넣은 규칙이 **정확히 그 사고를 통과시켰다.**

**★★ 되돌릴 수 없었다**
당시에는 **"수정 API가 없다"** 고 판단했다. 추측한 경로(`/invoices/correction`, `/invoices/update`)가 전부 404였기 때문이다.

**그 판단이 틀렸다.** 수정 경로는 있었고, 이름이 다를 뿐이었다 — 입력은 `.../invoices`, 수정은 `.../updateInvoices`. **같은 명사 아래 동사가 붙을 거라 가정**했는데 **별개 동사 경로**였다. 검색 한 번에 나왔고 전건 복구했다.

★★ **추측한 URL의 404는 "기능이 없다"가 아니라 "경로를 모른다"이다.** → 아래 별도 항목 참조

⚠️ **복구가 가능했다는 사실이 사고를 가볍게 만들지는 않는다.** 잘못된 값은 실제로 고객에게 보였고, 복구는 그걸 되돌린 게 아니라 **덮은 것**이다.

★ **비가역 쓰기는 사전 검증 말고는 방어 수단이 없다.** 사후 교정 경로가 있을 거라 가정하고 설계하면 안 된다.

**규율**

1. **검증기를 짤 때, 그 검증기가 잡아야 할 결함의 형태가 정상 목록에 있는지 본다**
2. ★ **탐지 규칙은 과거 사고 사례로 역검증한다.** 실제로 났던 오류를 넣어보고 **걸리는지 확인**한다. 안 걸리면 그 규칙은 없는 것과 같다
3. 외부에 쓰는 값은 **형식 검증 + 대상 매칭을 둘 다** 건다. 하나만으로는 부족하다

**곁가지 — 도달하지 않아 무사했던 결함**
이 결함은 **몇 주 전에 이미 기록돼 있었다.** 그때는 쓰기가 실제로 상대 시스템에 **도달하지 않아서** 피해가 없었고, 그래서 "확인됨" 정도로 남았다.
★★ **도달하지 않아서 무사했던 결함은 고쳐진 것이 아니다.** 경로가 열리는 날 그대로 터진다.

## 실패 목록은 실패 기록이 아니라 "부재"로 구한다

**상황**
대량 등록 배치가 일일 한도에 걸려 **1,155건 중 333건이 거부**됐다. 어떤 것이 실패했는지 목록이 필요하다.

**틀린 방법 — 결과 CSV의 `FAIL` 파싱**
★ **CSV 컬럼 구조가 스크립트마다 다르다.** 배치를 여럿 굴리다 보면 열 순서·헤더 이름·구분자가 조금씩 갈리고, **파싱이 조용히 깨진다.** 그러면 실패 목록이 비거나 엉뚱해진다.

**맞는 방법 — 대상 시스템에 없는 것으로 역산**
보내려던 전체 목록에서 **"등록 완료 목록에 없는 것"** 을 뺀다.

★★ **실패 기록은 기록하는 쪽의 형식에 의존하지만, 부재는 대상 시스템의 사실이다.**

**왜 이게 일반적인가**
- 실패 기록은 **쓰기가 성공해야 남는다.** 프로세스가 중간에 죽으면 그 구간은 실패 기록조차 없다
- 부재는 **중간에 무슨 일이 있었든 상관없이** 성립한다
- ★ 같은 이유로 **"몇 건 성공"보다 "무엇이 아직 없는가"가 재실행 대상으로 안전하다**

**한도 자체에 대한 곁가지**
그 한도는 **상품 수가 아니라 옵션(variant) 수 기준**이었다. **옵션이 많은 상품은 훨씬 빨리 한도를 먹는다** — 같은 건수를 보내도 소진 속도가 다르다. ★ **한도의 단위가 내가 세는 단위와 같은지 먼저 확인한다.**

## 추측한 URL의 404는 "기능이 없다"가 아니다

**사고**
어떤 리소스를 수정하는 경로를 찾으면서 **이름을 추측해서** 두 개를 시도했다.

```
POST .../invoices/correction   → 404
POST .../invoices/update       → 404
```

여기서 **"이 플랫폼에는 수정 API가 없다. 비가역이다"** 라고 결론 냈다. 그 결론으로 **수동 복구 작업을 계획**하고, **문서에 "비가역"이라고 적었고**, 다른 사람에게도 그렇게 보고했다.

**틀렸다.** 검색 한 번에 실제 경로가 나왔다.

```
POST .../orders/updateInvoices
```

★ **입력은 `.../invoices`, 수정은 `.../updateInvoices`.**
**같은 명사 아래 동사가 붙을 것**이라고 가정했는데, 실제로는 **별개의 동사 경로**였다. 리소스 트리를 따르는 REST 관례를 상대가 지킬 거라고 믿은 게 전부였다.

**★★ 규칙**

1. **경로를 추측했다면 404는 근거가 아니다.** 판정 전에 **"이 URL을 내가 추측했나"** 를 먼저 자문한다
2. **"기능이 없다"는 문서·검색·문의를 거친 뒤에만** 말한다
3. ★ **"비가역"이라는 판정은 특히 비싸다.** 그 한 마디가 **수동 작업, 설계 변경, 사과**를 만든다. 비가역이라고 말하기 전에 **한 번 더 찾는다**

**★★★ 곁가지 — 이 규칙은 이미 적혀 있었다**

이틀 전, 다른 엔드포인트에서 404를 받고 **이렇게 기록해뒀다.**

> **404를 "그런 기능이 없다"로 읽지 않는다. 경로를 아직 못 찾은 것이다.**

**그리고 이틀 뒤에 그걸 어겼다.** 같은 주에 비슷한 일이 세 번 있었다 — 검증기가 자기가 잡을 결함을 통과시켰고, 형식 규칙을 정해놓고 그 규칙을 어겼고, 이번엔 **판정 규칙을 적어놓고 판정 순간에 꺼내지 않았다.**

★★ **규칙을 적는 것과 판정하는 순간에 그 규칙을 꺼내는 것은 별개의 능력이다.**
적어두는 것만으로는 안 되고, **판정 직전에 자동으로 걸리는 자리**(체크리스트·린트·리뷰 질문)에 넣어야 실제로 작동한다.

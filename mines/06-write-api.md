# 쓰기 API · 응답을 믿지 않는 법

플랫폼 커머스 API를 상대로 반년을 굴리며 모았다. **특정 플랫폼 이야기가 아니다** — 승인 워크플로가 있고, 부분 수정을 지원하고, 상태를 문자열로 주는 **모든 쓰기 API**에서 같은 형태가 나온다.

한 문장으로 요약하면 이렇다.

> **어떤 응답도 성공의 증거가 아니다. 재조회만이 증거다.**

---

## 성공 응답이 거짓말하는 다섯 가지 방식

하루에 다섯 종류를 다 겪은 날이 있어서 표로 굳혔다.

| 응답 | 실제 상황 |
|---|---|
| `200` + `code=ERROR` | 심사중 리소스를 수정하려 했다. **HTTP는 200이다** |
| `200` + `rows=0` | **존재하지 않는 enum 값**으로 필터링했다. 에러가 아니라 빈 결과다 |
| `200` + `code=SUCCESS` + **미반영** | 부분 업데이트가 조용히 무시됐다. 26분 뒤에도 값이 그대로다 |
| `200` + `code=SUCCESS` + 경고 | 경고가 붙었지만 **실제로는 반영됐다.** 경고를 실패로 읽으면 정상 건을 재시도한다 |
| `400 PRECONDITION_FAILED` | 그냥 **존재하지 않는 경로**다. 조건 위반이 아니다 |

★ **성공과 실패의 축이 최소 세 개다** — HTTP 상태, 응답 본문의 `code`, 그리고 **재조회했을 때의 실제 값**. 앞의 둘이 다 통과해도 세 번째가 다를 수 있다.

**강제 장치**

```python
def ok(code, resp):
    return code == 200 and isinstance(resp, dict) and resp.get("code") != "ERROR"
```

이걸 안 넣어 **700여 건을 헛돌렸다.** 전부 거부됐는데 진행 파일에는 성공으로 기록됐다.

**그리고 이걸로도 부족하다.** 위 표의 3번은 `ok()`를 통과한다. 쓰기 후에는 **반드시 단건 재조회**로 실제 값을 확인한다. 변경 이력 엔드포인트가 있으면 그게 더 확실하다.

**역방향 — 실패로 보이는 성공**
쓰기 성공 응답의 `message`가 문자열 `"[]"`로 왔다. 빈 배열이 아니라 **빈 배열처럼 생긴 truthy 문자열**이다. `if msg:`로 오류를 판정하던 코드가 정상 반영된 건들을 실패로 기록했다. 빈 값의 표현은 타입마다 다르다 — `""` · `[]` · `"[]"` · `{}` · `null`. **존재 여부가 아니라 내용으로 판정**한다.
★ **오염된 실패 목록은 그 위에 쌓은 진단을 전부 무효로 만든다.** 그 "실패" 건들을 근거로 "기존 값이 원인"이라는 틀린 진단을 세웠고, 진범은 따로 있었다. 판정 함수 하나가 틀리면 배치 결과뿐 아니라 그 결과로 내린 결론까지 버려야 한다.

**여섯 번째 — 거부 목록을 안 읽었다**
추적 등록 API가 `accepted`와 `rejected`를 **따로** 돌려주는데, 래퍼가 거부 쪽을 무시하고 전건을 로컬 DB에 "등록됨"으로 기록했다. 운송사 자동 감지 실패로 거부된 건이 조회 불가 상태로 방치됐다. `accepted` 개수를 세고, 0이면 경고한다.
★ **그리고 `accepted`도 끝이 아니다.** 등록은 됐는데 추적은 "없음"인 경우가 있다 — "접수됨"은 등록 성공이지 추적 성공이 아니다. **성공에 한 겹이 더 있다.**

## HTTP 상태코드를 안 보면 400을 "0건"으로 읽는다

**증상**
주문 조회가 **0건**을 반환했다. "미발송 없음"으로 판정하고 넘어갔다. 실제로는 **미이행 9건이 방치**돼 있었고 그중 4건은 기한을 넘긴 상태였다.

**원인**
조회 기간을 40일로 잡았는데 그 API의 상한이 **32일 미만**이었다.

```
"endTime-startTime range should less than 32 day."
```

**HTTP 400이었다.** 그런데 코드가 `data` 배열의 길이만 세고 있었으니 `len([]) == 0` → "0건"이 됐다.

★ **응답 본문만 보고 상태코드를 안 보면, 모든 4xx가 0건으로 둔갑한다.**

**해법**
조회 래퍼에서 상태코드를 먼저 검사하고, 2xx가 아니면 **0을 반환하지 말고 예외를 던진다.** "0건"과 "조회 실패"를 같은 값으로 돌려주는 함수는 호출자를 반드시 속인다.

**같은 형태 — 공개 지리 데이터 API**
검색 반경 파라미터를 상한(10,000m)의 세 배로 올렸다. API는 에러를 돌려줬고, 수집기는 **"문서 0개"로 정상 종료**했다. 로그를 안 봤으면 몇 시간을 헛돌았다.
★ **상한이 있으면 값을 키우지 말고 호출 지점을 늘린다.** 중심점 하나의 반경을 키우는 대신 **중심 + 사방 4개 지점으로 타일링**하고 제목으로 dedupe한다. 범위를 넓히는 방법은 둘뿐이고, 상한이 있으면 후자만 남는다.
★ **수집기는 0건을 정상으로 넘기지 않는다.** "0건"은 경고로 찍는다 — 진짜 0건이면 사람이 한 번 보면 되고, 가짜 0건이면 그 경고가 유일한 단서다.

## 서명에서 쿼리스트링이 빠지면 401이 "0건"으로 보인다

**증상**
목록 조회가 계속 0건. 인증은 통과하는 줄 알았다.

**원인**
HMAC 서명 대상 문자열에 **쿼리스트링이 빠져 있었다.** 실제 응답은 `401 Invalid signature`.

★ **결함이 오래 안 드러난 이유가 있다** — 쿼리를 안 쓰는 엔드포인트(상품 API)에서는 서명이 맞았다. **쿼리를 쓰는 엔드포인트에서만** 터졌다.

**대가**
0건을 사실로 받아들여 판정을 내렸고, **그 판정으로 판매 중이던 항목을 내렸다**(복구했다).

**발견의 실마리 — 기록해둘 값어치가 있다**
**관리 화면에는 매출이 찍혀 있는데 API는 0을 줬다.** 그 불일치가 단서였다.

★ **0을 근거로 비가역 작업을 하기 전에 다른 경로와 대조한다.**

**같은 0이라도 다르다**
다른 채널의 조회도 0건이었는데 그건 **진짜 0**이었다 — **응답 원문을 눈으로 확인해 확정**했다.
**확인 절차를 거친 0과 그렇지 않은 0은 다른 값이다.**

## 부분 업데이트가 조용히 무시된다

**증상**
`PATCH`/부분 `PUT`에 본문을 실어 보내면 `200` + `SUCCESS`가 오는데 **값이 안 바뀐다.**

**파장**
배치가 **6주간 아무것도 바꾸지 못했다.** 진행 파일의 `ok:1500`은 *보내려 한 문자열의 길이*였지 *저장 결과*가 아니었다. 표본 40건 중 90%가 원본 그대로였고, 그건 배치 실패가 아니라 **등록 시점 원본이 그대로 남아 있는 것**이었다.

**변인 통제로 확정한 과정**
처음엔 페이로드 구조를 의심했다. 그래서 **구조 6종**(단순 div / img / table / ul / 큰따옴표 포함 / 공백 보존)을 전부 시도했다. **전부 실패했다.**
★ **6종이 다 같은 결과면 그건 구조 문제가 아니다.** 변인을 바꿔봐야 그 변인이 원인이 아님을 확정할 수 있다.

**확정된 경로**
승인 완료 상태에서는 **전체 PUT만 반영된다.**
1. 전체 PUT (id 없이, 승인요청 플래그 off) → **초안으로 강등되면서 값 반영**
2. 승인 요청 → 승인 완료 복귀

⚠️ **이 경로는 위험을 하나 만든다.** 전체 PUT은 **일시적으로 판매중단 상태**를 거친다. 대량으로 돌리면 그만큼이 동시에 판매중단된다. **소량 배치로 쪼개고, 회차마다 상태 재조회로 복귀를 확인**한다. 초안으로 두고 방치하는 게 진짜 사고다.

**전체 PUT이 실패해도 "아무 일도 없었다"가 아니다**
전체 PUT이 400으로 거부됐는데 **승인요청 해제는 이미 반영**돼 있었다. 거부된 항목들이 초안에 갇혀 판매중단 상태가 됐다. **쓰기 실패 ≠ 무변경.** 실패 응답을 받은 뒤에도 상태를 재조회한다.
같은 배치에서 두 가지가 더 나왔다.
- 성공 응답의 `message`가 문자열 `"[]"`로 와서 `if msg:`가 성공을 실패로 기록했다 — 앞 항목 "성공 응답이 거짓말하는 다섯 가지 방식"의 역방향이다
- 한 필드를 바꾸는 배치에 **목적과 무관한 속성 보강 함수**를 얹었더니, 그 함수가 허용목록 밖 값을 만들어 배치 전체를 죽였다. ★ **"이왕 하는 김에"가 실패율을 만든다. 한 배치는 한 가지만 바꾼다.**

**안전망 — 초안에 남은 것을 주기적으로 건진다**
30분마다 도는 작업이 초안 상태 전량을 조회해 승인을 다시 요청하고, **건수가 임계를 넘으면 경고**한다. 소량 배치로 쪼개는 것은 예방이고, 이건 사고가 났을 때 판매중단이 방치되는 시간을 30분으로 묶는 장치다.

## 후속 호출을 즉시 하면 무시된다

**증상**
값 변경 → 곧바로 승인 요청. 승인이 안 걸린다. 혹은 걸렸다가 되돌아간다.

**원인**
쓰기가 반영되기 전에 다음 호출이 도착한다. **두 호출을 체이닝하면 37/37 전건 실패**한 적이 있다.

**해법**
- 두 호출을 **분리**한다
- **2·4·6·8초 대기 후 재시도 4회** + 매 회차 **상태 재조회**로 확인
- 최종 실패는 별도 코드로 진행 파일에 남긴다. 그래야 잔류분을 나중에 셀 수 있다

★ **응답이 200이라는 건 "요청이 접수됐다"이지 "다음 호출이 이걸 볼 수 있다"가 아니다.**

## 등록 시점에만 정할 수 있는 필드가 있다

**증상**
분류 코드를 고치려는데, 부분 PUT도 전체 PUT도 **200을 주고 값이 안 바뀐다.** 승인 완료와 초안 **두 상태 모두**에서 확인했다.

**확정 사례**
수십 건이 이름·브랜드 수정을 거쳤는데 분류 코드는 **전건 그대로**였다. 아우터가 폰 액세서리 분류에 들어가 있었고 **고칠 방법이 없었다.**

**해법이 없다는 게 해법이다**
오분류면 **삭제 후 재등록**뿐이다. 그리고 심사·제재 중인 항목은 삭제도 막히므로 그마저 불가능하다.

★ **등록 시점에 확정해야 하는 값이 무엇인지, 등록 코드를 짜기 전에 확인한다.** 나중에 고치면 된다고 가정하지 않는다.

**같은 성질을 다른 채널에서도 만났다** — 카테고리 ID가 등록 후 변경 불가(`NotChangable`)였다. **채널이 달라도 같은 제약이 나온다면 그건 우연이 아니라 도메인의 성질**이다.

**하위 리소스는 단위가 다르다**
상위 항목 경로에 판매중지를 걸면 **404**다. 판매중지·재고변경은 상위 항목이 아니라 **그 안의 하위 리소스(옵션 단위) ID**로만 된다. 404를 "기능이 없다"로 읽기 전에 **하위 리소스 경로부터 찾는다.** 어떤 작업이 어느 단위에 붙는지는, 등록 시점 확정값과 마찬가지로 등록 코드를 짜기 전에 확인할 목록이다.

## 필드가 일방통행일 수 있다

**증상**
브랜드 필드를 공란으로 되돌리려 하니 **400**.

```
"브랜드명은 제출 후 변경할 수 없습니다"
```

공란 → 값은 되고, **값 → 공란은 안 된다.**

★ **잘못 넣으면 영구다.** 되돌릴 수 있다고 가정하고 쓰지 않는다.

**곁가지 — 내가 틀렸던 것**
"브랜드가 공란이면 승인이 고착한다"고 기록했다가 **정정**했다. 공란이어도 통과한다. 고착의 진짜 원인은 앞 항목의 **연속 호출**이었다. 상관을 인과로 읽은 것이다.

## 상태 필드의 이름이 상태를 뜻하지 않는다

**세 가지가 한꺼번에 나왔다.**

**1. 판매를 중지해도 `statusName`은 `'승인완료'`로 유지된다.**
실제 판매 여부는 별도 엔드포인트의 `onSale`·`재고수량`에 있다. 승인 상태와 판매 상태는 **다른 축**이다.

**2. 삭제된 항목도 `statusName='상품삭제'`로 조회된다.**
★ **존재 여부로 삭제를 판정하면 안 된다.** 목록에 있으니 살아있다고 읽으면 이미 지워진 걸 다시 처리한다. 이 오판으로 배치 두 개가 20~30분마다 같은 일을 무한 반복했다.

**3. 상태 문자열이 접두어를 공유한다.**
`임시저장`과 `임시저장중`이 **별개 문자열로 둘 다 존재**한다.

```python
if status == '임시저장':      # 임시저장중을 누락한다
if status.startswith('임시저장'):   # 이게 맞다
```

★ **상태값을 `==`로 비교하기 전에 실제로 존재하는 값을 전수로 뽑아본다.** 문서에 없는 값이 나온다.

## "전체 상태로 확대했다"는 목록이 전체가 아니었다

**증상**
목록 조회에 상태 필터가 **필수**인 API에서, 특정 구간의 레코드가 **조회에 아예 안 나온다.** 존재하는데 어떤 조합으로도 안 잡힌다.

**원인**
필터 목록에서 **한 상태가 빠져 있었다.** 그 상태는 "송장은 입력됐지만 배송 스캔 전"에 해당하는, **짧게 머무는 중간 구간**이었다.

★ 더 나쁜 건, **6개월 전에 이 목록을 "전체로 확대"라고 적어뒀다는 것**이다. 실제로는 이름이 비슷한 다른 값(`NONE`)을 넣고 진짜 값(`NONE_TRACKING`)을 빠뜨렸다. **"전체"라고 쓰여 있으니 아무도 다시 대조하지 않았다.**

**대가**
해당 구간의 주문을 **이틀간 못 찾았다.** 대응이 필요한 건이었다.

**해법**
- 필터 값은 **문서가 아니라 실제 enum과 대조**한다
- ★ **"전체"라고 적는 순간 다음 사람이 검증을 건너뛴다.** 목록을 적을 땐 **무엇으로 확인했는지 같이 적는다**
- ★ **이름이 비어 보이는 상태를 조심한다.** `NONE_TRACKING`은 "추적 없음"처럼 읽히지만 실제로는 **"아직 스캔 전"** 이다. 이름이 성질을 오도하면 목록에서 빠뜨리기 쉽다

★★ **필터가 필수인 목록 API에서, 빠뜨린 값은 곧 존재하지 않는 레코드다.**
"없다"고 결론 내리기 전에 **필터부터 의심한다.**

**곁가지 — 반대편도 막힌다**
그 구간의 레코드는 조회에 안 보이지만 **이미 처리가 끝나 있을 수 있다.** 안 보인다고 미처리로 단정하고 다시 쓰기를 시도하면 `INVALID_STATUS`로 거부된다. **보이지 않는 것과 처리되지 않은 것은 다르다.**

**필터가 필수인 목록은 그 파라미터의 값 공간만큼만 보인다**
상태 필터가 필수인 목록 API에서는 **열거하지 못한 값의 구간이 영영 안 보인다.** 전수를 봐야 하면 목록을 고치는 게 아니라 **필터가 필요 없는 단건 경로**를 찾는다. 단건 경로는 상태와 무관하게 조회됐고, 목록에 없던 필드까지 돌려줬다.
★ **같은 조각으로 이뤄진 두 경로가 다른 리소스다.** `/{상위}/{id}/하위`와 `/{상위}/하위/{id}`는 **순서만 다른데**, 하나는 주문 ID를 받고 다른 하나는 다른 종류의 ID를 기대해 400을 냈다. 경로 조각의 순서도 식별자다.

## 존재하지 않는 enum은 에러가 아니라 0건이다

**증상**
상태 필터로 조회했더니 0건. "해당 상태인 항목이 없다"로 읽었다.

**원인**
필터 값이 **존재하지 않는 enum**이었다(`APPROVING`이라고 썼는데 실제는 `IN_REVIEW`). **에러가 안 난다.** `200`에 빈 배열이 온다.

**해법**
필터 값은 문서가 아니라 **실제 데이터에서 뽑는다.** 전체를 한 번 조회해 그 필드의 distinct 값을 세어보면 끝난다.

★ **모수를 함께 센다.** `0/N`에서 N을 모르면 0의 의미도 모른다.

## 빈 응답은 상태가 아니다

**증상**
단건 조회가 빈 객체 `{}` 를 돌려줬다. **수십 건 전부 "판매중지"로 판정**하고 **백여 건에 불필요한 재개 호출**을 실행했다.

**실제**
**전부 정상 판매중**이었다. 그 단건 조회 경로 자체가 `PRECONDITION_FAILED`였다 — 즉 **조회가 아예 성립하지 않았다.**

★ **조회가 성립했는지부터 확인한다.** 빈 응답에서 상태를 읽어내지 않는다.

**같은 형태를 자동화도 밟았다**
재고 감시 배치가 **외부 조회 실패를 "품절"로 판정**하고 있었다. 소스가 차단당해 빈 값을 주면 곧바로 품절 목록에 들어갔다.
→ **`_srcfail` 플래그로 조회 실패와 실제 상태를 분리**했다. 그리고 **조회실패가 실제 품절의 2배를 넘고 10건 이상이면** "판정 신뢰 불가" 경고를 띄운다.

★ **"실패"를 나타내는 별도 값이 없으면 실패는 반드시 어떤 정상값으로 위장한다.**

## 404를 "삭제됨"으로 읽지 마라

**증상**
목록에 있는 항목이 API 단건 조회에서 404. 표본 30건 중 절반 이상.

**원인**
**소유권 밖**이라는 뜻이었다. 다른 도구가 만든 항목이라 우리 토큰으로는 안 보인다. **일부는 403**이 나왔다 — **403이 섞여 나오면 확정**이다(존재하지만 권한이 없다).

**해법**
- 배치 전에 **목록을 API 조회로 필터링**한다
- 목록 API의 `status` 값은 **소유권을 보증하지 않는다**
- 검색 응답을 그대로 저장한 목록은 **검증되지 않은 상태**임을 전제한다

★ **404는 "없다"가 아니라 "이 자격으로는 안 보인다"이다.**

---

## "목록에서 사라짐"을 상태 전이로 판정하지 마라

**증상**
활성 목록에서 항목이 사라져서 **취소 알림을 보냈다.** 실제로는 그대로 있었고 취소 카운트는 0, **이미 이행까지 끝난 건**이었다. 원인은 조회 시점 누락 또는 **페이지네이션 미완**.

**해법**
- **해당 상태를 직접 조회해서 실제로 발견돼야만** 그 상태로 판정한다
- 못 찾으면 **보류**한다. 부재는 판정 근거가 아니다
- 검증 조회 대상 상태를 **전체로 확대**한다

★ **오탐 비용이 크다** — 이 판정은 외부에 취소 요청을 넣는 행동으로 이어진다.

---

## 배치마다 대상 목록의 소스가 다르다

**증상**
필터 파일을 만들어 배치에 물렸더니 **0건 처리.**

**원인**
필터는 A 파일 기준으로 만들었는데 **배치는 B 파일을 읽고 있었다.** 같은 대상을 가리키는 것처럼 보이는 목록이 셋 있었고 셋 다 건수가 달랐다.

| 배치 | 목록 소스 | 건수 |
|---|---|---|
| 배치 A | 진행 파일 | 4천여 |
| 배치 B | API 실시간 조회 | 8천 |
| (참고) | 별도 수집분 | 8천 |

**해법**
**필터 파일은 배치의 목록과 교집합으로 만든다.** 계정·환경별로 타겟 파일을 분리한다.

★ **"0건 처리"를 보면 대상이 없는 게 아니라 목록이 어긋난 것부터 의심한다.**

---

## 요약 문구는 사유가 아니다

**증상**
거부 알림에 **"담당자 검토 결과 반려되었습니다"**. 이건 **상태 문구지 사유가 아니다.** 실제 사유는 이력 엔드포인트의 `comment`에 있다.

**대가**
4건이 같은 품목군이라 **카테고리 규제로 판정**하고 관련 수십 건에 차단 플래그를 걸었다. 실제 사유는 전량 **'이미지 규격'**이었다. **전건 철회**했다.

★ **같은 배치로 등록된 항목은 같은 결함을 공유한다.** 품목군 동시 거부는 우연일 수 있다.

**한 번 더 — 이력 조회가 갈랐다**
수백 건 중 2건이 거부됐다. 직전에 이름 교정 배치를 돌린 뒤였으니 **교정을 원인으로 의심하기 쉬웠다.** 이력을 보니 **교정 전에도 같은 사유로 거부**돼 있었다.

★ **변경 직후의 증상을 그 변경 탓으로 읽지 않는다. 이력이 그걸 가른다.**

---

## 등록 당시 통과했다고 지금도 통과하지 않는다

**증상**
문제없이 등록된 항목을 다시 저장하려니 **400**으로 거부된다.

**원인**
플랫폼이 중간에 **필수 항목 검증을 강화**했다. 기존 데이터는 그대로 살아있지만, **다시 쓰는 순간 현행 정책 검증을 탄다.**

**구체적 거부 조건**
- 필수 속성에 값이 없거나 `'상세설명 참조'` 같은 회피 문구면 거부
- **빈 문자열도 거부.** 실제 값이 있어야 한다
- 선택형 필드는 **허용값 목록 안에서만** 고를 수 있다
- **항목 이름 중복 금지** — 같은 이름을 일괄 대입하면 거부된다. 값을 접미로 붙여 유일화한다

**해법**
- 속성을 **빼면 안 된다.** 빼면 "필수 항목 없음"으로 바뀐다. **삭제가 아니라 값 대체**다
- 허용값은 **메타 엔드포인트로 조회**해서 그 안에서 고른다

★ **오래된 데이터를 대량으로 다시 쓰는 작업은 "수정"이 아니라 "현행 기준 재등록"이다.** 통과율을 그렇게 예상해야 한다.

**주의 — 반대 사례도 있다**
필수값 누락은 "값 대체"가 맞지만, **값이 중복이면 채우는 게 아니라 단일로 접는 게 맞았다.** 130여 건 중 실패 15건이 이 경우였다. **한 처방을 전건에 적용하지 않는다.**

**발원지를 막지 않으면 교정은 재생산된다**
기존 항목을 고치는 동안에도 **등록 파이프라인이 필수 속성마다 `'상세설명 참조'`를 무조건 주입**하고 있었다. 교정 배치가 아무리 돌아도 신규 등록분이 같은 결함을 다시 만든다. 기존분 교정과 발원지 차단은 별개의 작업이고, 후자를 먼저 한다.
★ **같은 문구가 필드에 따라 갈린다.** 고시정보 필드의 `'상세페이지 참조'`는 허용되고, 속성 필드의 같은 문구는 400이다. 금지 문구는 필드 단위로 판정한다.

**메타를 축약해 저장하면 제약이 사라진다**
카테고리 메타가 속성마다 **단위·허용 단위·입력 타입**을 주는데, 스키마를 이름과 필수 여부만 남기고 저장했다. 그래서 `"30"` 같은 순수 숫자를 단위 없이 보냈고 거부됐다. 메타의 단위와 입력 타입을 **보존**하고, 순수 숫자면 기본 단위를 **결합**하고, 허용 단위 밖이면 **호출 전에 차단**한다(목록이 없으면 통과 — 없는 제약을 만들지 않는다).
★ **오류 문구의 "혹은" 뒤쪽이 진범이었다.** 앞 절만 읽고 가설을 세워 며칠을 버렸다. **원문의 모든 절을 용의선상에 둔다.**

## 폴백이 자기 산출물을 다시 먹는다

**증상**
진행 파일에는 성공(`ok:225`)으로 찍히는데, 최근 처리분이 **전부 정확히 225자**로 동일하다.

**원인**
3단 폴백이 **"기존 데이터 재활용"** 이었다. 1단이 항상 실패하고 있었고(원본에 해당 필드가 아예 없었다), 그래서 3단이 **자기가 앞서 만든 껍데기를 다시 읽어 또 껍데기를 만들었다.**

**해법**
**자기 산출물을 소스로 삼는 폴백은 차단한다.** 원본이 없으면 실패로 남기는 게 정직하다.

★ **길이가 찍혀 있어도 내용이 자기 복제면 그건 산출물이 아니다.**
★ **출력값이 여러 건에서 정확히 동일하면 그 자체가 신호다.**

## 번들의 표면 파일만 갈면 내부는 옛 정체성을 가리킨다

**증상**
배포 번들의 진입 파일(`index.html`)을 새것으로 교체하고 출시했는데, **옛 이름·옛 아이콘이 뜨고 CDN이 접근 거부**를 낸다. 새 화면은 보이지도 않는다.

**원인**
번들 내부의 셸 부트스트랩에 **정체성이 하드코딩**돼 있었다.

```
name              ← 셸이 이 이름으로 자기 자산 경로를 찾는다 → 접근 거부
deploymentId      ← 이 값으로 화면을 소환한다. 안 바꾸면 구버전이 계속 뜬다
브랜드 표시명 / 색상 / 아이콘  ← 헤더에 옛 정체성이 노출된다
```

**표면 파일만 교체한 번들은 출시돼도 새 화면이 안 보일 수 있다.** 코드는 들어갔는데 배선이 없는 상태다.

★ **"파일을 갈았다"와 "그 파일이 실제로 소환된다"는 다르다.**
템플릿·도너 번들을 이식할 때는 **내부 부트스트랩이 참조하는 식별자를 전수로 찾아 치환**한다. 무결성 메타데이터(크기·해시)가 있으면 그것도 재계산해야 한다.

**미해결로 남긴 것**
`deploymentId`를 플랫폼이 등록 시점에 재발급한다면 이 처방으로도 안 될 수 있다. **다음 검수를 리트머스로 잡고, 실패하면 이식을 접고 공식 빌드체인으로 전환**하기로 했다. — 처방에 확신이 없으면 **판정 기준과 철수 조건을 미리 적어둔다.**

## PUT이 200 SUCCESS를 주는데 한 필드만 영영 안 바뀐다 — 상위 필드가 남의 반영을 막는다

**증상**
통관 플래그를 켜는 PUT이 **200 `SUCCESS`**를 돌려준다. 재조회하면 값이 그대로다. 페이로드를 바꿔봐도, 상태를 바꿔봐도 같다. 수천 건 전량이 이 상태였다.

**원인**
그 항목의 **배송방법 필드**가 특정 값이면 통관 플래그가 **무시된다.** 통관 플래그 자체엔 아무 문제가 없다 — **다른 필드가 이 필드의 운명을 정한다.** 그리고 배송방법 필드는 등록 시점 확정값이라 바꾸려 하면 400이다.

앞의 "등록 시점에만 정할 수 있는 필드"와 "일방통행 필드"는 **자기 자신이 안 바뀌는** 것이었다. 이건 **자기가 안 바뀌면서 남까지 막는다.** 새 형태다.

★ **안 먹는 필드를 보지 말고 그 필드를 지배하는 상위 설정을 찾는다.** 안 먹는 필드를 아무리 들여다봐도 원인이 안 나온다. 범인이 다른 필드이기 때문이다.

**두 번째 사례 — "누락" 400이 값을 요구하는 게 아니다**
브랜드 상품 등록에 `"제품 식별번호 누락"` 400이 떴다. 값을 채웠더니 **오히려 계속 거부**됐다.
**브랜드 필드에 값이 있으면** 그 검증이 걸리고, **브랜드를 비우면 검증 자체가 사라진다.** "누락"은 "값을 넣으라"가 아니라 **"이 조합이 성립하지 않는다"**는 뜻이었다.

★ **에러 메시지가 지목하는 필드가 원인인 경우가 오히려 드물다.** 막히면 값을 채우는 방향만 보지 말고, **검증을 유발하는 필드를 끄는 방향**도 본다. (브랜드는 일방통행이라 공란으로 시작하는 쪽이 선택지를 남긴다.)

**앞 항목과 반대 처방이다 — 구분해야 한다**
"등록 당시 통과했다고 지금도 통과하지 않는다"는 **"삭제가 아니라 값 대체"**다. 그건 필수 속성이라 빼면 다른 에러로 바뀌는 경우다. 여기는 **검증을 유발하는 필드가 따로 있는** 경우다. 메커니즘이 다르므로 처방도 반대다. **한 처방을 모든 400에 적용하지 않는다.**

**해법**
- 지배당하는 필드는 고칠 수 없으니 **정상 조합으로 복제 재등록**한다. 원본은 지우지 않는다 — 삭제하면 노출이 절반이 된다
- 신규 등록 코드는 **지배하는 필드부터 확정**한다. 나중에 못 바꾼다

**검증**
★ **정상 등록분 표본을 열어보는 것이 문서보다 빠르다.** 두 번째 사례의 답은 추론이 아니라 **잘 팔리고 있는 항목 4건을 그냥 열어봐서** 나왔다 — 식별번호 속성 셋이 전부 빈 문자열이었다. 통과하는 페이로드가 이미 계정 안에 있다. 되는 것을 손에 넣고 나란히 놓는다.
그리고 **한 층을 걷어내면 그 아래 층이 드러난다.** 400을 없앤 뒤 "정상 처리 재개 2천여 건"을 기록했지만 허수였다 — 400이 사라졌을 뿐 값은 여전히 안 들어갔다. 거부가 사라진 것과 값이 반영된 것은 다른 사건이다.

## 반려는 있는데 감시 큐는 비어 있다 — 큐가 조용히 비는 세 가지 방식

승인 워크플로를 감시하는 큐 하나에서 사흘 동안 세 가지가 나왔다. 셋 다 예외 없이, 로그 없이, **항목이 관측 밖으로 나간다.**

**① 카드 제목이 약속한 집합보다 소스 필터가 좁다**
대시보드 카드 제목은 "반려 감시"인데, 소스가 감시 큐뿐이었다. 그 큐는 `submitted`·`unknown`만 고른다 — **`rejected`를 구조적으로 제외**한다. 옆 카드가 "REJECTED 2건"을 찍는 동안 이 카드는 "감시 중인 반려 건이 없습니다"라고 말했다. **화면이 자기 제목을 반박했다.**
큐를 넓히지 않았다(감시 = "아직 판정 전"이라는 뜻이 흐려진다). **읽는 함수를 따로 두고** 카드가 둘을 합쳐 라벨로 갈라 보여준다.
★ **카드 제목은 계약이다.** 필터가 뜻을 좁히면 **제목을 좁히거나 소스를 늘린다** — 둘 중 하나는 해야 한다.

**② 상태를 확정 필드가 아닌 부수 신호로 판정했다**
감시 상태 판정이 `comment` **유무만** 봤다. 그래서 반려가 아닌 메모 한 줄("임시저장 되었습니다", "담당자 배정 완료")이 항목을 `rejected`로 앉히고 **큐 밖으로 밀어냈다.**
두 겹이었다. 반려 표기가 하나도 없으면 마지막 comment를 그냥 돌려주는 **폴백**이 있었고("조용한 누락 방지"가 의도였다), 상태 판정 함수는 확정 상태 필드를 이미 들고 있으면서도 `"rejected" if comment else "unknown"`으로 텍스트 유무만 봤다.
★ **"사유가 있다"와 "반려다"는 다른 명제다.** 조용한 누락을 막으려던 폴백이 반려 아닌 것을 반려로 만들어 **더 조용한 누락**을 낳았다. **안전장치가 판정 근거로 승격되면 그 자체가 결함이다.** 폴백은 제거가 아니라 용도 축소 — 메모는 사람이 화면에서 읽는 용도로만 남기고, 상태는 확정 필드로만 정한다.
★ **반쪽 수리 주의.** 판정만 고치면 안 된다 — 큐가 받는 상태 목록에 새 미확정 상태가 없으면 판정이 맞아도 **행은 그대로 큐를 떠난다.** 판정과 큐 목록은 한 뜻의 이중 구현이라 둘을 묶는 계약을 둔다: 미확정 상태 집합 ⊆ 큐가 받는 상태 집합.
부검이 한 번에 바닥까지 닿지도 않았다 — 처음엔 "이 동작은 옳고 재무장이 없던 게 결함"이라 썼고, 그것도 틀렸다. **한 겹 고치면 그 밑이 보인다.**

**③ 처방이 관측 상태를 갱신하지 않는다**
재제출(승인 재요청) 함수는 마켓에 요청을 보내고 `{success: true}`만 돌려준다. 대장의 status는 **손대지 않는다.** 그래서 이미 큐를 떠난 행(`rejected`)에 처방을 걸면 — 요청은 실제로 나가고 항목은 다시 심사 큐에 들어가지만, 대장은 여전히 `rejected`라 **다음 회전이 그 항목을 안 본다.** 결과를 아무도 확인하지 않는다.
**처방을 열심히 실행할수록 관측 밖으로 나간다.** 이게 이 결함의 모양이다.
02장 "upsert가 워크플로 상태를 되돌린다"의 정반대다 — 거기선 수집기가 상태를 리셋해서 사람의 조치가 지워졌고, 여기선 조치가 상태를 안 건드려서 감시가 죽는다.
★ **상태를 바꾸는 행위는 관측 상태도 같이 바꿔야 한다.** "대장은 마켓이 뭐라 답했나를 적는다"는 원칙은 옳지만, *우리가 다시 물어봤다*는 것도 사실이고 그 사실이 관측 대상 여부를 정한다.
- **성공 시에만** 대장을 `submitted`로 되돌린다. 실패를 "다시 심사 중"으로 만들면 가짜 수치다
- **재제출 경로 전부에** 건다. 네 경로의 밑바닥이 같은 함수였다 — 하나만 걸면 나머지가 그대로 사슬을 끊는다
- 소급용 재무장 버튼은 마켓 호출 없이 대장만 되돌린다. 다음 스캔이 실제 상태로 덮으므로 자기복구된다

**검증**
회전마다 한 줄을 찍는다: `큐 잔류 N · 졸업 M · saved a · unknown b · approved c`. 어느 상태에 몇 건이 있는지 세지 않으면 셋 중 어느 것도 보이지 않는다. 그리고 순서가 있다 — 판정을 고쳐도 대장이 이미 `rejected`면 첫 회전엔 안 잡힌다. **재무장으로 되돌린 뒤 다음 회전부터다.** 이 순서를 놓치면 "수리했는데 왜 안 보이냐"가 된다.

## 바디 없는 PUT이 411 Length Required로 끊긴다

**증상**
승인 요청은 **보낼 바디가 없는 PUT**이다. 응답이 `411 Length Required`인데 본문이 **HTML**로 온다(`<html><title>411 Length Required</title>`). 이 API의 다른 응답은 전부 JSON이라 "중계가 깨졌나"로 먼저 읽힌다. 아니다.

**원인**
흔한 HTTP 클라이언트는 바디를 안 주면 **`Content-Length` 헤더를 아예 안 붙인다.** 게이트웨이는 길이 없는 PUT을 411로 끊는다. HTML은 게이트웨이의 에러 페이지가 중계를 거쳐 그대로 온 것이다. 중계가 바디를 벗긴 게 아니라 **애초에 실을 바디가 없었다.**
★ **바디가 없는 것과 길이를 안 밝히는 것은 다르다.** HTTP는 전자를 허용하지만 게이트웨이는 후자를 거부한다.

**해법**
페이로드를 발명하지 않는다(`{}`도 임의값이다). **빈 바디 + 길이 0을 명시**한다.

```python
body = b''
headers['Content-Length'] = '0'
```

(요청 서명이 method·path·date만 쓴다면 바디를 바꿔도 서명은 불변이다 — 이 수정은 인증을 건드리지 않는다.)

**관문이 둘이다**
클라이언트만 고쳐도 안 끝났다. 요청이 **고정 IP 중계**를 거쳐 나가므로 관문이 하나 더 있다. 중계가 빈 바디일 때 curl의 POSTFIELDS를 **조건부로** 세팅하고 있었다.

```php
if ($body !== null && $body !== '') curl_setopt($ch, CURLOPT_POSTFIELDS, $body);
```

읽으면 오히려 방어적으로 보인다 — "빈 바디를 굳이 세팅할 이유가 있나?" 그게 함정이다. **빈 바디를 세팅하는 것이 곧 길이 0을 선언하는 것**이라 여기선 조건이 곧 결함이다. 바디가 비어도 항상 세팅하고, 호출부가 준 `Content-Length`는 버리고 실제 바이트 수로 다시 계산한다(어긋나면 게이트웨이가 끊는다).
★ **경유가 있으면 관문도 그만큼 늘어난다.** 우리 쪽을 고쳐도 중계가 흘리면 그대로다. 첫 수리의 mock이 직결 경로만 검사해서 초록이 떴다 — 그래서 이 사실을 늦게 알았다.

**파급**
411 하나가 네 겹으로 번졌다: 승인요청이 안 걸림 → 항목이 초안에 머묾 → 초안은 사유 텍스트가 없어 감시 분류에서 "미분류"로 떨어짐 → 대시보드 카드가 그걸 못 보여줌(앞 항목의 ①). **화면 어디에도 안 뜨는 채로 이틀.**

**검증**
★ **오류가 다른 층으로 옮겨 가는 것(411 → 401)이 수리의 증거다.** 중계 배포 뒤 같은 호출이 411 대신 401을 냈다. 411이 사라졌다는 건 curl이 길이를 붙였다는 뜻이고, 남은 401은 인증 층의 문제다. 전송 계층이 끝났으니 다음 층으로 갈 수 있다. 조용해지는 것보다 옮겨 가는 것이 낫다. 그 뒤 `success: true`, 그 뒤 심사 큐 진입 — **각 단계가 다음 단계의 증거**다.

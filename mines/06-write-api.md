# 쓰기 API · 응답을 믿지 않는 법

플랫폼 커머스 API를 상대로 반년을 굴리며 모았다. **특정 플랫폼 이야기가 아니다** — 승인 워크플로가 있고, 부분 수정을 지원하고, 상태를 문자열로 주는 **모든 쓰기 API**에서 같은 형태가 나온다.

한 문장으로 요약하면 이렇다.

> **어떤 응답도 성공의 증거가 아니다. 재조회만이 증거다.**

---

## 성공 응답이 거짓말하는 다섯 가지 방식

하루에 다섯 종류를 다 겪은 날이 있어서 표로 굳혔다.

| 응답 | 실제 상황 |
|---|---|
| `200` + `code=ERROR` | 심사중 리소스를 수정하려 했다. **HTTP는 200이다** |
| `200` + `rows=0` | **존재하지 않는 enum 값**으로 필터링했다. 에러가 아니라 빈 결과다 |
| `200` + `code=SUCCESS` + **미반영** | 부분 업데이트가 조용히 무시됐다. 26분 뒤에도 값이 그대로다 |
| `200` + `code=SUCCESS` + 경고 | 경고가 붙었지만 **실제로는 반영됐다.** 경고를 실패로 읽으면 정상 건을 재시도한다 |
| `400 PRECONDITION_FAILED` | 그냥 **존재하지 않는 경로**다. 조건 위반이 아니다 |

★ **성공과 실패의 축이 최소 세 개다** — HTTP 상태, 응답 본문의 `code`, 그리고 **재조회했을 때의 실제 값**. 앞의 둘이 다 통과해도 세 번째가 다를 수 있다.

**강제 장치**

```python
def ok(code, resp):
    return code == 200 and isinstance(resp, dict) and resp.get("code") != "ERROR"
```

이걸 안 넣어 **700여 건을 헛돌렸다.** 전부 거부됐는데 진행 파일에는 성공으로 기록됐다.

**그리고 이걸로도 부족하다.** 위 표의 3번은 `ok()`를 통과한다. 쓰기 후에는 **반드시 단건 재조회**로 실제 값을 확인한다. 변경 이력 엔드포인트가 있으면 그게 더 확실하다.

## HTTP 상태코드를 안 보면 400을 "0건"으로 읽는다

**증상**
주문 조회가 **0건**을 반환했다. "미발송 없음"으로 판정하고 넘어갔다. 실제로는 **미이행 9건이 방치**돼 있었고 그중 4건은 기한을 넘긴 상태였다.

**원인**
조회 기간을 40일로 잡았는데 그 API의 상한이 **32일 미만**이었다.

```
"endTime-startTime range should less than 32 day."
```

**HTTP 400이었다.** 그런데 코드가 `data` 배열의 길이만 세고 있었으니 `len([]) == 0` → "0건"이 됐다.

★ **응답 본문만 보고 상태코드를 안 보면, 모든 4xx가 0건으로 둔갑한다.**

**해법**
조회 래퍼에서 상태코드를 먼저 검사하고, 2xx가 아니면 **0을 반환하지 말고 예외를 던진다.** "0건"과 "조회 실패"를 같은 값으로 돌려주는 함수는 호출자를 반드시 속인다.

---

## 서명에서 쿼리스트링이 빠지면 401이 "0건"으로 보인다

**증상**
목록 조회가 계속 0건. 인증은 통과하는 줄 알았다.

**원인**
HMAC 서명 대상 문자열에 **쿼리스트링이 빠져 있었다.** 실제 응답은 `401 Invalid signature`.

★ **결함이 오래 안 드러난 이유가 있다** — 쿼리를 안 쓰는 엔드포인트(상품 API)에서는 서명이 맞았다. **쿼리를 쓰는 엔드포인트에서만** 터졌다.

**대가**
0건을 사실로 받아들여 판정을 내렸고, **그 판정으로 판매 중이던 항목을 내렸다**(복구했다).

**발견의 실마리 — 기록해둘 값어치가 있다**
**관리 화면에는 매출이 찍혀 있는데 API는 0을 줬다.** 그 불일치가 단서였다.

★ **0을 근거로 비가역 작업을 하기 전에 다른 경로와 대조한다.**

**같은 0이라도 다르다**
다른 채널의 조회도 0건이었는데 그건 **진짜 0**이었다 — **응답 원문을 눈으로 확인해 확정**했다.
**확인 절차를 거친 0과 그렇지 않은 0은 다른 값이다.**

## 부분 업데이트가 조용히 무시된다

**증상**
`PATCH`/부분 `PUT`에 본문을 실어 보내면 `200` + `SUCCESS`가 오는데 **값이 안 바뀐다.**

**파장**
배치가 **6주간 아무것도 바꾸지 못했다.** 진행 파일의 `ok:1500`은 *보내려 한 문자열의 길이*였지 *저장 결과*가 아니었다. 표본 40건 중 90%가 원본 그대로였고, 그건 배치 실패가 아니라 **등록 시점 원본이 그대로 남아 있는 것**이었다.

**변인 통제로 확정한 과정**
처음엔 페이로드 구조를 의심했다. 그래서 **구조 6종**(단순 div / img / table / ul / 큰따옴표 포함 / 공백 보존)을 전부 시도했다. **전부 실패했다.**
★ **6종이 다 같은 결과면 그건 구조 문제가 아니다.** 변인을 바꿔봐야 그 변인이 원인이 아님을 확정할 수 있다.

**확정된 경로**
승인 완료 상태에서는 **전체 PUT만 반영된다.**
1. 전체 PUT (id 없이, 승인요청 플래그 off) → **초안으로 강등되면서 값 반영**
2. 승인 요청 → 승인 완료 복귀

⚠️ **이 경로는 위험을 하나 만든다.** 전체 PUT은 **일시적으로 판매중단 상태**를 거친다. 대량으로 돌리면 그만큼이 동시에 판매중단된다. **소량 배치로 쪼개고, 회차마다 상태 재조회로 복귀를 확인**한다. 초안으로 두고 방치하는 게 진짜 사고다.

## 후속 호출을 즉시 하면 무시된다

**증상**
값 변경 → 곧바로 승인 요청. 승인이 안 걸린다. 혹은 걸렸다가 되돌아간다.

**원인**
쓰기가 반영되기 전에 다음 호출이 도착한다. **두 호출을 체이닝하면 37/37 전건 실패**한 적이 있다.

**해법**
- 두 호출을 **분리**한다
- **2·4·6·8초 대기 후 재시도 4회** + 매 회차 **상태 재조회**로 확인
- 최종 실패는 별도 코드로 진행 파일에 남긴다. 그래야 잔류분을 나중에 셀 수 있다

★ **응답이 200이라는 건 "요청이 접수됐다"이지 "다음 호출이 이걸 볼 수 있다"가 아니다.**

## 등록 시점에만 정할 수 있는 필드가 있다

**증상**
분류 코드를 고치려는데, 부분 PUT도 전체 PUT도 **200을 주고 값이 안 바뀐다.** 승인 완료와 초안 **두 상태 모두**에서 확인했다.

**확정 사례**
수십 건이 이름·브랜드 수정을 거쳤는데 분류 코드는 **전건 그대로**였다. 아우터가 폰 액세서리 분류에 들어가 있었고 **고칠 방법이 없었다.**

**해법이 없다는 게 해법이다**
오분류면 **삭제 후 재등록**뿐이다. 그리고 심사·제재 중인 항목은 삭제도 막히므로 그마저 불가능하다.

★ **등록 시점에 확정해야 하는 값이 무엇인지, 등록 코드를 짜기 전에 확인한다.** 나중에 고치면 된다고 가정하지 않는다.

**같은 성질을 다른 채널에서도 만났다** — 카테고리 ID가 등록 후 변경 불가(`NotChangable`)였다. **채널이 달라도 같은 제약이 나온다면 그건 우연이 아니라 도메인의 성질**이다.

## 필드가 일방통행일 수 있다

**증상**
브랜드 필드를 공란으로 되돌리려 하니 **400**.

```
"브랜드명은 제출 후 변경할 수 없습니다"
```

공란 → 값은 되고, **값 → 공란은 안 된다.**

★ **잘못 넣으면 영구다.** 되돌릴 수 있다고 가정하고 쓰지 않는다.

**곁가지 — 내가 틀렸던 것**
"브랜드가 공란이면 승인이 고착한다"고 기록했다가 **정정**했다. 공란이어도 통과한다. 고착의 진짜 원인은 앞 항목의 **연속 호출**이었다. 상관을 인과로 읽은 것이다.

## 상태 필드의 이름이 상태를 뜻하지 않는다

**세 가지가 한꺼번에 나왔다.**

**1. 판매를 중지해도 `statusName`은 `'승인완료'`로 유지된다.**
실제 판매 여부는 별도 엔드포인트의 `onSale`·`재고수량`에 있다. 승인 상태와 판매 상태는 **다른 축**이다.

**2. 삭제된 항목도 `statusName='상품삭제'`로 조회된다.**
★ **존재 여부로 삭제를 판정하면 안 된다.** 목록에 있으니 살아있다고 읽으면 이미 지워진 걸 다시 처리한다. 이 오판으로 배치 두 개가 20~30분마다 같은 일을 무한 반복했다.

**3. 상태 문자열이 접두어를 공유한다.**
`임시저장`과 `임시저장중`이 **별개 문자열로 둘 다 존재**한다.

```python
if status == '임시저장':      # 임시저장중을 누락한다
if status.startswith('임시저장'):   # 이게 맞다
```

★ **상태값을 `==`로 비교하기 전에 실제로 존재하는 값을 전수로 뽑아본다.** 문서에 없는 값이 나온다.

## 존재하지 않는 enum은 에러가 아니라 0건이다

**증상**
상태 필터로 조회했더니 0건. "해당 상태인 항목이 없다"로 읽었다.

**원인**
필터 값이 **존재하지 않는 enum**이었다(`APPROVING`이라고 썼는데 실제는 `IN_REVIEW`). **에러가 안 난다.** `200`에 빈 배열이 온다.

**해법**
필터 값은 문서가 아니라 **실제 데이터에서 뽑는다.** 전체를 한 번 조회해 그 필드의 distinct 값을 세어보면 끝난다.

★ **모수를 함께 센다.** `0/N`에서 N을 모르면 0의 의미도 모른다.

## 빈 응답은 상태가 아니다

**증상**
단건 조회가 빈 객체 `{}` 를 돌려줬다. **수십 건 전부 "판매중지"로 판정**하고 **백여 건에 불필요한 재개 호출**을 실행했다.

**실제**
**전부 정상 판매중**이었다. 그 단건 조회 경로 자체가 `PRECONDITION_FAILED`였다 — 즉 **조회가 아예 성립하지 않았다.**

★ **조회가 성립했는지부터 확인한다.** 빈 응답에서 상태를 읽어내지 않는다.

**같은 형태를 자동화도 밟았다**
재고 감시 배치가 **외부 조회 실패를 "품절"로 판정**하고 있었다. 소스가 차단당해 빈 값을 주면 곧바로 품절 목록에 들어갔다.
→ **`_srcfail` 플래그로 조회 실패와 실제 상태를 분리**했다. 그리고 **조회실패가 실제 품절의 2배를 넘고 10건 이상이면** "판정 신뢰 불가" 경고를 띄운다.

★ **"실패"를 나타내는 별도 값이 없으면 실패는 반드시 어떤 정상값으로 위장한다.**

## 404를 "삭제됨"으로 읽지 마라

**증상**
목록에 있는 항목이 API 단건 조회에서 404. 표본 30건 중 절반 이상.

**원인**
**소유권 밖**이라는 뜻이었다. 다른 도구가 만든 항목이라 우리 토큰으로는 안 보인다. **일부는 403**이 나왔다 — **403이 섞여 나오면 확정**이다(존재하지만 권한이 없다).

**해법**
- 배치 전에 **목록을 API 조회로 필터링**한다
- 목록 API의 `status` 값은 **소유권을 보증하지 않는다**
- 검색 응답을 그대로 저장한 목록은 **검증되지 않은 상태**임을 전제한다

★ **404는 "없다"가 아니라 "이 자격으로는 안 보인다"이다.**

---

## "목록에서 사라짐"을 상태 전이로 판정하지 마라

**증상**
활성 목록에서 항목이 사라져서 **취소 알림을 보냈다.** 실제로는 그대로 있었고 취소 카운트는 0, **이미 이행까지 끝난 건**이었다. 원인은 조회 시점 누락 또는 **페이지네이션 미완**.

**해법**
- **해당 상태를 직접 조회해서 실제로 발견돼야만** 그 상태로 판정한다
- 못 찾으면 **보류**한다. 부재는 판정 근거가 아니다
- 검증 조회 대상 상태를 **전체로 확대**한다

★ **오탐 비용이 크다** — 이 판정은 외부에 취소 요청을 넣는 행동으로 이어진다.

---

## 배치마다 대상 목록의 소스가 다르다

**증상**
필터 파일을 만들어 배치에 물렸더니 **0건 처리.**

**원인**
필터는 A 파일 기준으로 만들었는데 **배치는 B 파일을 읽고 있었다.** 같은 대상을 가리키는 것처럼 보이는 목록이 셋 있었고 셋 다 건수가 달랐다.

| 배치 | 목록 소스 | 건수 |
|---|---|---|
| 배치 A | 진행 파일 | 4천여 |
| 배치 B | API 실시간 조회 | 8천 |
| (참고) | 별도 수집분 | 8천 |

**해법**
**필터 파일은 배치의 목록과 교집합으로 만든다.** 계정·환경별로 타겟 파일을 분리한다.

★ **"0건 처리"를 보면 대상이 없는 게 아니라 목록이 어긋난 것부터 의심한다.**

---

## 요약 문구는 사유가 아니다

**증상**
거부 알림에 **"담당자 검토 결과 반려되었습니다"**. 이건 **상태 문구지 사유가 아니다.** 실제 사유는 이력 엔드포인트의 `comment`에 있다.

**대가**
4건이 같은 품목군이라 **카테고리 규제로 판정**하고 관련 수십 건에 차단 플래그를 걸었다. 실제 사유는 전량 **'이미지 규격'**이었다. **전건 철회**했다.

★ **같은 배치로 등록된 항목은 같은 결함을 공유한다.** 품목군 동시 거부는 우연일 수 있다.

**한 번 더 — 이력 조회가 갈랐다**
수백 건 중 2건이 거부됐다. 직전에 이름 교정 배치를 돌린 뒤였으니 **교정을 원인으로 의심하기 쉬웠다.** 이력을 보니 **교정 전에도 같은 사유로 거부**돼 있었다.

★ **변경 직후의 증상을 그 변경 탓으로 읽지 않는다. 이력이 그걸 가른다.**

## 등록 당시 통과했다고 지금도 통과하지 않는다

**증상**
문제없이 등록된 항목을 다시 저장하려니 **400**으로 거부된다.

**원인**
플랫폼이 중간에 **필수 항목 검증을 강화**했다. 기존 데이터는 그대로 살아있지만, **다시 쓰는 순간 현행 정책 검증을 탄다.**

**구체적 거부 조건**
- 필수 속성에 값이 없거나 `'상세설명 참조'` 같은 회피 문구면 거부
- **빈 문자열도 거부.** 실제 값이 있어야 한다
- 선택형 필드는 **허용값 목록 안에서만** 고를 수 있다
- **항목 이름 중복 금지** — 같은 이름을 일괄 대입하면 거부된다. 값을 접미로 붙여 유일화한다

**해법**
- 속성을 **빼면 안 된다.** 빼면 "필수 항목 없음"으로 바뀐다. **삭제가 아니라 값 대체**다
- 허용값은 **메타 엔드포인트로 조회**해서 그 안에서 고른다

★ **오래된 데이터를 대량으로 다시 쓰는 작업은 "수정"이 아니라 "현행 기준 재등록"이다.** 통과율을 그렇게 예상해야 한다.

**주의 — 반대 사례도 있다**
필수값 누락은 "값 대체"가 맞지만, **값이 중복이면 채우는 게 아니라 단일로 접는 게 맞았다.** 130여 건 중 실패 15건이 이 경우였다. **한 처방을 전건에 적용하지 않는다.**

## 폴백이 자기 산출물을 다시 먹는다

**증상**
진행 파일에는 성공(`ok:225`)으로 찍히는데, 최근 처리분이 **전부 정확히 225자**로 동일하다.

**원인**
3단 폴백이 **"기존 데이터 재활용"** 이었다. 1단이 항상 실패하고 있었고(원본에 해당 필드가 아예 없었다), 그래서 3단이 **자기가 앞서 만든 껍데기를 다시 읽어 또 껍데기를 만들었다.**

**해법**
**자기 산출물을 소스로 삼는 폴백은 차단한다.** 원본이 없으면 실패로 남기는 게 정직하다.

★ **길이가 찍혀 있어도 내용이 자기 복제면 그건 산출물이 아니다.**
★ **출력값이 여러 건에서 정확히 동일하면 그 자체가 신호다.**

## 번들의 표면 파일만 갈면 내부는 옛 정체성을 가리킨다

**증상**
배포 번들의 진입 파일(`index.html`)을 새것으로 교체하고 출시했는데, **옛 이름·옛 아이콘이 뜨고 CDN이 접근 거부**를 낸다. 새 화면은 보이지도 않는다.

**원인**
번들 내부의 셸 부트스트랩에 **정체성이 하드코딩**돼 있었다.

```
name              ← 셸이 이 이름으로 자기 자산 경로를 찾는다 → 접근 거부
deploymentId      ← 이 값으로 화면을 소환한다. 안 바꾸면 구버전이 계속 뜬다
브랜드 표시명 / 색상 / 아이콘  ← 헤더에 옛 정체성이 노출된다
```

**표면 파일만 교체한 번들은 출시돼도 새 화면이 안 보일 수 있다.** 코드는 들어갔는데 배선이 없는 상태다.

★ **"파일을 갈았다"와 "그 파일이 실제로 소환된다"는 다르다.**
템플릿·도너 번들을 이식할 때는 **내부 부트스트랩이 참조하는 식별자를 전수로 찾아 치환**한다. 무결성 메타데이터(크기·해시)가 있으면 그것도 재계산해야 한다.

**미해결로 남긴 것**
`deploymentId`를 플랫폼이 등록 시점에 재발급한다면 이 처방으로도 안 될 수 있다. **다음 검수를 리트머스로 잡고, 실패하면 이식을 접고 공식 빌드체인으로 전환**하기로 했다. — 처방에 확신이 없으면 **판정 기준과 철수 조건을 미리 적어둔다.**

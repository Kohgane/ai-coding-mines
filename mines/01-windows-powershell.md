# Windows · PowerShell

Windows PowerShell 5.1을 전제로 한다. 대부분 **에러 없이 결과만 조용히 깨진다.**

---

## PowerShell 5.1이 UTF-8 파일을 CP949로 읽는다

**증상**
UTF-8로 저장된 파일을 `Get-Content`로 읽어 가공한 뒤 되쓰면 한글이 자기파괴된다. 예외는 없다.

**원인**
PS 5.1의 `Get-Content` 기본 인코딩은 시스템 ANSI 코드페이지(한국어 Windows는 949)다. UTF-8 바이트를 949로 해석해 문자열로 만든 시점에서 이미 손상됐고, 되쓸 때 그 손상이 파일에 박힌다.

**해법**
- 읽기: `-Encoding UTF8` 명시
- 쓰기: `New-Object System.Text.UTF8Encoding($false)` + `[IO.File]::WriteAllText` (BOM 없이)

`Out-File`/`Set-Content`의 기본 인코딩도 신뢰하지 않는다. 다른 도구가 읽을 파일이면 항상 명시한다.

**검증**
쓰기 후 다시 읽어 원본 문자열과 비교한다. 눈으로 콘솔 출력만 보면 콘솔 코드페이지가 한 번 더 개입해 판정이 흐려진다.

## BOM 없는 .ps1의 한글 리터럴이 깨진다

**증상**
스크립트를 UTF-8(BOM 없음)로 저장했더니 `powershell.exe` 실행 시 소스에 박은 한글 문자열이 깨진 채 출력된다. 주석 속 한글은 무해하고, 죽는 건 **출력 문자열과 한글 경로**다.

**원인**
BOM이 없으면 PS 5.1 파서가 스크립트 소스 자체를 시스템 ANSI(949)로 읽는다. 앞 항목이 *데이터 파일 I/O* 문제라면, 이건 *스크립트 소스*가 파싱되는 단계의 문제다. 둘은 다른 층이다.

**해법**
BOM을 붙이면 해결되지만 "BOM 없이 저장" 규율과 충돌한다. 규율을 지켜야 하면:

- 소스를 **순수 ASCII**로 두고 한글만 런타임 디코딩한다.
  ```powershell
  function U($b64) { [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($b64)) }
  ```
- 한글이 들어간 경로는 리터럴로 쓰지 말고 `$env:USERPROFILE` 등으로 조립한다.

**검증**
`LC_ALL=C grep -n '[^ -~]' script.ps1` — 출력이 없으면 순수 ASCII다.

## 네이티브 exe에 `2>&1`을 걸면 exit 0인데 `$?`가 false

**증상**
`git` 같은 네이티브 실행 파일이 정상 종료(exit 0)했는데 `$?`가 false이고, git의 평범한 진행 메시지가 빨간 에러로 쏟아진다.

**원인**
PS 5.1은 네이티브 exe의 stderr에 `2>&1`을 걸면 **각 줄을 ErrorRecord로 포장**한다. stderr에 뭔가 썼다는 사실만으로 실패 취급이 된다. 많은 CLI가 정상 진행 상황을 stderr로 보낸다.

**해법**
네이티브 명령에 `2>&1`을 걸지 않는다. 출력을 삼켜야 하면 감싼다.
```powershell
try { & $exe @args 2>&1 | Out-Null } catch { }
```

**검증**
`$LASTEXITCODE`를 본다. 네이티브 명령의 성패는 `$?`가 아니라 이 값이다.

## 커밋 메시지의 큰따옴표가 인자를 쪼갠다

**증상**
```
git commit -m "... "ok:1284"처럼 ..."
error: pathspec '남길' did not match any file(s) known to git
```

**원인**
PowerShell이 인자를 네이티브 exe로 넘기기 전에 재파싱한다. 문자열 안의 큰따옴표가 인용을 끊고, 그 자리부터 공백에서 인자가 쪼개진다. 메시지 중간의 단어가 갑자기 pathspec이 된다.

**해법**
- 메시지에 큰따옴표를 쓰지 않는다 (가장 확실하다)
- 필요하면 작은따옴표, 백틱 이스케이프, 또는 `git commit --file <임시파일>`
- 여러 줄 메시지는 single-quoted here-string `@'...'@` — 닫는 `'@`는 **반드시 0열**에 둔다

**검증**
`git log -1 --format=%B`로 실제 저장된 메시지를 본다.

## 환경변수 키에 비ASCII를 쓸 수 없다

**증상**
환경변수 키에 한글을 넣었더니 셸·PaaS 콘솔·`os.environ` 어디선가 안 먹거나 깨진다. 값이 아니라 **키** 쪽이다.

**원인**
환경변수 키의 인코딩은 플랫폼·셸마다 보장 범위가 다르다. 값은 대체로 통과해도 키는 통과하지 못하는 경로가 있다.

**해법**
키는 **로마자 + 대문자 + 언더스코어**로 확정한다. 접두어로 그룹을 나눠야 하면 로마자 접두어를 쓴다.

## 터미널 프롬프트 위에 여러 줄을 붙여넣지 않는다

**증상**
Username/암호 입력 프롬프트가 떠 있는 상태에서 명령 블록을 붙여넣으면, 뒤따르는 명령들이 **입력값으로 삼켜진다.** 비밀번호 자리에 다음 명령이 들어가는 사고로 이어진다.

**해법**
블록을 쪼개고, 프롬프트가 조용해진 뒤 다음 블록을 붙인다.

## heredoc으로 이모지를 밀어넣으면 스크립트가 죽는다

**증상**
셸 heredoc 안에 파이썬 코드를 쓰고 그 안에 이모지를 넣었더니 서러게이트 쌍이 깨져 스크립트가 죽는다.

**원인**
셸 → 파이썬으로 넘어가는 구간에서 인코딩이 **한 번 더** 갈린다. 경계마다 다른 규칙이 적용된다.

**해법**
1. heredoc으로 밀어넣지 말고 **파일에 쓴 뒤 실행**한다
2. 이스케이프 코드가 아니라 **이모지 문자 그대로** 넣는다

대량 패치를 heredoc으로 치지 않는 규율과 같은 이유다.

---

## 인코딩은 도구 경계마다 한 번씩 갈린다 (총론)

텍스트가 도구 경계를 넘을 때마다 인코딩 규칙이 바뀐다. **어느 쪽도 에러를 내지 않는다.** 결과물만 조용히 깨진다.

| 경계 | 증상 |
|---|---|
| 파일 → `Get-Content` | UTF-8을 949로 읽고 되써서 한글 자기파괴 |
| 파일 → powershell.exe 파서 | BOM 없으면 소스가 ANSI로 읽혀 리터럴 깨짐 |
| 셸 heredoc → 파이썬 | 이모지 서러게이트 쌍 파손 |
| PS → 네이티브 exe 인자 | 큰따옴표 재파싱으로 인자 분할 |
| 코드 → 환경변수 키 | 비ASCII 키가 안 먹거나 깨짐 |

**원칙**
1. **경계는 파일로 넘긴다.** 인라인 문자열로 대량 텍스트를 밀어넣지 않는다
2. **비ASCII를 리터럴로 두지 않는다.** 소스가 어떤 코드페이지로 읽힐지 보장되지 않으면 런타임 디코딩이나 로마자로 우회한다
3. **넘긴 뒤 한 번 찍어 확인한다.** 경계를 통과한 직후의 실물을 눈으로 본다

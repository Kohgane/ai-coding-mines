## `requirements.txt` 누락 → 무증상 롤백

**증상**
새로 추가한 라우트만 404. 앱 자체는 정상(다른 라우트 전부 200). git push 성공, 원격에 파일도 등록줄도 존재, 서버에서 로컬 import도 통과. 8분을 기다려도 404.

**원인**
`requirements.txt`에 `requests`가 없었다. 클린 빌드에서 새 모듈 import 실패 → 앱 기동 실패 → **PaaS가 직전 성공 빌드로 계속 서비스**했다. 그래서 "앱은 멀쩡한데 새 라우트만 없는" 상태가 된다.

**왜 놓치기 쉬운가**
기존 코드가 이미 `requests`를 쓰는데도 requirements에 없었다. 기존 컨테이너에 캐시로 남아 돌고 있었을 뿐이고, **클린 빌드에서만 터진다.**

**철칙**
1. 새 모듈 추가 시 import 목록과 `requirements.txt`를 **대조**한다
2. 배포 후 새 라우트가 404면 **가장 먼저 의존성을 의심**한다 (커밋 유실이 아니다)
3. **push 성공 메시지는 배포 성공의 증거가 아니다.** 실 URL로 친다
4. **로컬 import 성공은 배포 성공의 증거가 아니다**

## 런타임이 읽는 파일이 이미지에 안 들어간다

**증상**
로컬·CI 유닛테스트는 전부 그린인데(레포에 파일이 실재하므로) **배포본에서만** 404/400/파일 없음. 같은 유형으로 3회 재발했다.

**원인 패턴**
라우트가 상대경로(`Path("data/x.json")`)로 읽는데 그 파일이 이미지에 없다. 근원이 둘로 겹치기도 한다.
1. Dockerfile이 해당 디렉터리를 COPY하지 않음
2. `.dockerignore`가 그 디렉터리를 통째로 제외 — **빌드 컨텍스트에서부터 배제**

**해법**
- **디렉터리 통째 COPY를 기본**으로 한다. 개별 파일 COPY는 신규 산출물 누락이 재발한다
- 런타임 생성물이 섞인 디렉터리는 통째 COPY가 불가하므로 → **필수 정적 파일만 명시 COPY + `.dockerignore`에 `!` 재포함**
- CI에서 이미지 빌드 후 `test -f /app/data/*.json`으로 **존재를 실증**하고 없으면 잡을 실패시킨다

**점검 습관**
런타임이 읽는 경로를 추가·이동할 때마다 **3자 대조**: (1) Dockerfile COPY (2) `.dockerignore` 제외 (3) 라우트 상대경로 vs WORKDIR

**검증 요령 (base 이미지를 못 받는 환경에서)**
`.dockerignore`는 base 이미지와 무관하다. `FROM scratch`로 동일한 `COPY`만 빌드하면 컨텍스트 포함 여부가 그대로 검증된다 — 제외됐으면 "not found in build context"로 실패한다.

## 512MB 인스턴스에서 ffmpeg가 워커를 통째로 죽인다

**증상 (OOM이라고 안 써 있어서 못 알아본다)**
- 가벼운 엔드포인트는 200인데 특정 요청만 502
- 로그에 OOM 문구 없이 `Instance restarted`만 반복
- 메모리 그래프가 상한까지 치솟았다 급락

**원인**
Python 프로세스가 떠 있는 상태에서 subprocess로 ffmpeg를 fork+exec 하면 순간 메모리가 튄다. 진짜 피크의 원인은 **libx264 재인코딩**이었다.

**해법 — 재인코딩을 하지 마라**
소스가 이미 h264 mp4면 오디오만 갈아끼우면 된다.

```bash
ffmpeg -i v.mp4 -i a.mp3 -map 0:v:0 -map 1:a:0 \
  -c:v copy -c:a aac -b:a 128k -shortest -movflags +faststart out.mp4
```

폴백: `-preset ultrafast -crf 28 -threads 1`

**참고**
로그에 `WEB_CONCURRENCY=1 by default`가 찍히면 최저사양 인스턴스가 확정이다.

## PaaS의 `/tmp`는 재배포·재시작마다 초기화된다

**증상**
생성한 파일을 나중에 쓰려니 `404 Not Found`. 같은 이유로 중간 단계에서 `다운로드 실패 HTTPError`도 재현된다.

**회피**
생성→가공→업로드를 **끊김 없이 연속 실행**하면 문제없다. 단 **"만들어두고 나중에 발행"·스케줄 발행은 불가**하다.

**해소**
산출물을 오브젝트 스토리지로 자동 업로드한다. 실패해도 기존 경로로 폴백하게 두면 동작이 안 깨진다.

## 동기 대량 라우트는 호출자 타임아웃에서 터진다

**증상**
건수가 많은 작업을 한 HTTP 요청 안에서 동기로 처리했더니 응답이 안 돌아온다. 부분 처리분은 커밋됐는데 응답이 없어 **진행 상태를 알 수 없다**(재시도하면 중복 위험).

**타임아웃은 하나가 아니다 — 이게 핵심이다**
이 지뢰를 네 번 밟는 동안 매번 **더 빡빡한 타임아웃이 하나씩 더 나왔다.**

| 축 | 성격 |
|---|---|
| 워커 타임아웃 | 내가 정한다. 늘릴 수 있다 |
| 외부 스케줄러 타임아웃 | **못 늘린다. 플랫폼 하드 상한이다** |
| 항목당 최악 지연 | 외부 의존이라 보장이 없다 |

★ **건수 캡(limit)은 시간 캡이 아니다.** `limit=10`에 항목당 최악 8초면 80초다. 워커 타임아웃은 안 넘는데 외부 스케줄러의 30초를 넘긴다.

**중간 처방과 그 한계 (남겨둘 값어치가 있다)**
처음엔 **벽시계 예산**으로 갔다 — 항목마다 착수 *전에* 경과를 확인하고, 예산에 닿으면 중단하고 `{처리분, 잔여, 예산소진}`을 200으로 반환. 남은 건 다음 호출이 이어받는다. 한 건씩 잡아 처리·커밋하면 중단 시 **미처리 잔재가 0**이 된다.

**이걸로도 안 됐다.** 두 가지 때문이다.
1. **예산이 22초여도 진행 중인 1건이 초과할 수 있다.** 하드 상한 앞에서는 "대체로 안에 든다"가 무의미하다
2. 한 라우트가 **무거운 작업 두 개를 스택**하고 있었다. 앞에만 예산을 걸었더니 뒤는 무예산으로 20~40초를 더 썼다. 게다가 **뒤 작업이 아예 못 돌아 굶었다** — 외부 스케줄러의 빨강은 **어느 홉이 굶었는지 안 알려준다**

**확정 처방 — 예산 역산이 아니라 즉답**
- 라우트는 **즉시 202만 반환**하고 실작업은 **백그라운드**로 넘긴다
- 스케줄러 판정 = **202 즉답 = 성공.** 실작업 결과는 로그로 본다
- **중복 진입 가드**를 둔다. 단 **다중 워커 안전의 근본은 멱등성**이고 락은 보조다
- **스레드가 스스로 종료**하게 예산을 건다. 순서를 지킨다:
  **작업 예산 < 스케줄러 간격 < 워커 타임아웃**
- 한 요청에 무거운 외부 I/O를 **두 개 스택하지 않는다.** 불가피하면 각 작업에 **최소 예산을 예약**해 굶김을 막는다

**결과**
`http=202 · 0.24초`. **즉답 설계라 큐 길이와 무관하게 상수 시간**이 된다. 하드 상한 대비 여유가 100배 이상이면 그 축은 고민 대상에서 사라진다.

**규율**
> 호출자의 타임아웃이 **플랫폼 하드 상한**이고 작업이 그 안에 안 끝날 수 있으면, 예산으로 깎지 말고 **즉답 + 백그라운드 + 멱등 재개 + 중복 가드**로 간다. **예산 깎기는 상한을 늘릴 수 있을 때만 유효하다.**

**상태 저장소를 따로 만들지 않는다**
작업 대상 자체를 상태로 쓴다(초안/발행/메타플래그가 곧 진행상태). 별도 잡스토어 없이 **무상태 재개**가 된다. 작업이 이미 멱등·재개 가능하면 백그라운드 스레드가 고아가 돼도 다음 호출이 이어받는다.

**후속 — 할 일이 0일 때의 비용을 먼저 본다**
잔여 0인데도 한 틱이 30초 넘게 걸렸다. 원인은 틱이 **전체 목록을 매번 두 번 조회**하는 것이었다. 할 일이 없어도 그 고정비를 태운다.
→ 수렴 후 **즉시 skip하는 완료 캐시**, 목록은 **틱당 1회만** 조회해 공유, 그리고 '대상 0'을 **대상 없음(정상) vs 조회 실패(이상)** 로 구분해 로그한다.
★ **주기 작업의 튜닝은 고정비를 없앤 뒤에 측정하고 결정한다.**

## API 스펙을 고정해도 값의 *포맷*까지 고정되진 않는다

**증상**
파서를 확정 스펙에 맞춰뒀는데, 날짜 필드가 예고 없이 `2026-08-18` → `2026-08-18 00:00:00+00`으로 바뀌어 소비자 쪽이 깨졌다.

**해법**
**필드명은 고정하되 값은 방어적으로 정규화**한다(날짜는 앞 10자만 등). 그리고 서버를 손볼 때 **소비자를 같이 확인**한다.

## 디스크가 차면 SSH가 끊기고 JSON 쓰기가 잘린다

**증상**
파일이 중간에서 잘려 깨진 채 저장된다. 새 SSH 세션이 안 열린다.

**원인**
CMS가 원본 + 썸네일 4~8종을 다 저장한다. 천여 건을 한 번에 올리자 10GB 한도가 하루 만에 찼다.

**방어 4중**
1. 업로드 시점에 원본을 축소(장변 1000px, q78)
2. 썸네일은 실사용 사이즈만 생성(실측해보니 4종뿐이었다)
3. 디스크 감시 크론
4. 업로더가 올리는 이미지 장수 제한

3분의 1을 회수했다.

## 공용 API의 동시 슬롯 제한을 서버 장애로 오진한다

**증상**
503이 뜬다. 서버 장애처럼 보인다.

**오진 경위 (기록해둘 값어치가 있다)**
"curl은 200인데 python urllib은 503" → **클라이언트 차이로 단정** → 곧바로 curl도 503. 실제로는 두 클라이언트가 **IP당 동시 슬롯 2개를 서로 뺏고 있었다.**
★ **관측 하나로 단정한 결과다.**

**철칙**
- 수집 스크립트를 **동시에 두 개 이상 띄우지 않는다**
- 상태 엔드포인트로 **슬롯 확인 후 요청**한다
- 503/504는 정상 동작 중의 잡음이다. **재시도·쿨다운으로 흡수**한다
- 미러는 대체로 더 불안정하다 — 폴백용으로만 쓴다

## 레이트리밋이 빡빡한 무료 지오코더는 갈아탄다

**증상**
공용 Nominatim은 초당 1회 + 일일 총량 제한. `RATE=1.15`도 429, `1.6`으로 올려도 429. 백오프가 300초까지 늘며 **17%에서 정체**. 1만여 건에 5시간 이상 + 차단 위험.

**해법**
Photon(Komoot) 역지오코딩으로 전환.

```
https://photon.komoot.io/reverse?lat=..&lon=..&lang=en
```

- 레이트리밋이 관대해 초당 약 3건으로 동작 확인
- 응답: `features[0].properties`의 `street` / `housenumber` / `district` / `city` / `countrycode`
- 표본 4/4 성공, 결과가 Nominatim보다 깨끗했다

## Gradio Space를 REST로 직접 호출할 때

`gradio_client` 패키지 없이 **2단계 REST**로 호출한다(런타임에 의존성 추가 불필요).

```
POST {base}/gradio_api/call/{fn}   body: {"data":[...]}   → event_id
GET  {base}/gradio_api/call/{fn}/{event_id}               → SSE에서 결과 URL 파싱
```

`base`는 `https://{owner}-{space}.hf.space` (소문자, `/`→`-`).

**1. 파라미터를 추측하지 말고 `info`로 확인한다**
`GET {base}/gradio_api/info` 의 `named_endpoints`에 함수명과 파라미터 순서·타입·기본값이 전부 있다.
추측으로 `predict`, `[prompt, '', w, h, 5]`를 넣었다가 전부 헛돌았다. 실제는 `/generate_video`에 `[prompt, aspect_ratio(Literal 문자열), steps, negative_prompt, ...]` 였다.

**2. float를 보내면 error, int여야 한다**
`rate`/`pitch`에 `0.0`(float)을 보내면 **`event: error`만 뱉고 끝난다.** `0`(int)이면 정상. **에러 본문이 `null`이라 원인이 안 보인다** — 동일 요청을 타입만 바꿔 비교해야 잡힌다.

**3. 토큰 없으면 error**
무기명 호출은 `event: error`. 무료 계정의 Read 토큰이면 충분하다.

**4. 결과 URL은 임시 경로다**
`{base}/gradio_api/file=/tmp/gradio/.../x.mp4` 형태. 접근은 되지만 휘발성이므로 받아서 즉시 스토리지에 올린다.

## Supabase 키 체계 개편과 RLS 오진

| 구분 | 접두어 | 용도 |
|---|---|---|
| Publishable key | `sb_publishable_` | 브라우저 노출 가능(구 anon) |
| Secret key | `sb_secret_` | 서버 전용, RLS 우회(구 service_role) |
| Legacy 탭 | `eyJ...`(JWT) | 구 anon/service_role, 아직 동작 |

`service_role`은 Legacy 탭으로 밀렸다. 현재 경로는 **Settings → API Keys → Secret keys**.

**anon 키로는 Storage 쓰기가 안 된다 — 그런데 오진을 부른다**
쓰기는 `new row violates row-level security policy`로 막히는데, **버킷 목록은 에러 없이 빈 배열만 반환**한다. 권한 문제가 아니라 "버킷이 없다"로 보인다.

**주의**
Secret/service_role은 **모든 RLS를 우회하는 마스터 키**다. 서버 환경변수 전용이며 프론트·공개 저장소 금지.

## WordPress REST: 인코딩된 슬래시가 404

**증상**
`/wp-json/wp/v2/plugins/{slug}%2F{file}` 형태가 404. 플러그인 활성/비활성 조작이 막힌다.

**원인**
Apache가 인코딩된 슬래시를 거부한다.

**우회**

```
POST https://example.org/index.php?rest_route=/wp/v2/plugins/wordpress-seo/wp-seo
body: {"status":"active"}
```

`rest_route` 쿼리 방식은 정상 동작(200).

**함께 밟은 것 — 활성 플러그인만 보고 판단 금지**
"SEO 플러그인이 없다"고 오판했는데 **설치돼 있고 비활성**이었다. `GET /wp-json/wp/v2/plugins`로 inactive 포함 전수 조회한다.

## Play Console: "프로덕션 출시됨"이 출시가 아닐 수 있다

**증상**
제출활동에 **프로덕션 출시됨**이 찍혔는데 스토어는 전 지역 404.

**원인**
Play는 *국가/지역·등록정보 변경*과 *버전(aab) 릴리스*를 **별개 열차로 굴린다.** 국가만 열린 **빈 프로덕션 트랙**이었고 aab는 테스트 트랙에만 실려 있었다.

**판정법 — 콘솔 표시를 믿지 말고 실측한다**

```bash
curl -s -o /dev/null -w "%{http_code}" -A "Mozilla/5.0" \
  "https://play.google.com/store/apps/details?id=<pkg>&gl=KR"
```

404면 미출시다. 대시보드의 프로덕션 **"비활성"** 도 같은 신호다.

**처방**
프로덕션 > 새 버전 만들기 > (라이브러리에서 추가) > 버전 검토 → **"프로덕션 트랙으로 출시 시작" 버튼까지 누른다.** 이 버튼을 안 누르면 영원히 안 나간다. 그 뒤 게시 개요에서 **검토를 위해 제출**.

**곁가지**
- **사전 등록 카드 절대 클릭 금지.** 누르면 *프로덕션 국가 전체 삭제 + 사전등록 활성*이 검토 큐에 올라가 정식 출시가 "출시 예정" 페이지로 바뀐다. 두 번 사고 났다 → 게시 개요 "변경사항 삭제"로 철회
- **관리형 게시 ON**이면 승인돼도 수동 "게시" 클릭 대기다
- 한 릴리스에 **번들 2개(versionCode 1·2)를 같이 올리면 오류.** 낮은 쪽을 뺀다
- 권장조치 4종(edge-to-edge·폐기 API·방향제한·R8)은 **차단이 아니다**

## 콘솔이 표시하는 업로드키 지문 ≠ 내 키스토어 지문

**증상**
`keytool -printcert -jarfile`로 확인되는 실제 인증서와 콘솔의 앱 무결성 화면이 **다른 지문**을 표시한다. 두 앱에서 재현됐다.

**처방 (표준)**
따지지 말고 **3키 전부 assetlinks에 주입**한다 — ①Play 앱 서명키 ②콘솔 표기 업로드키 ③내 빌드키. 어느 쪽이 진짜든 동작이 보장된다. 서버는 환경변수로 덮어쓸 수 있게 하되 기본값에 3키를 박아둔다.

**혼동 주의**
"잘못된 키로 서명됨" 오류가 뜨면 **앱을 잘못 고른 것부터 의심한다.** 다른 앱 화면에 이 앱의 aab를 올려서 난 오류였다(우상단 앱 배지 확인이 최우선).

```bash
unzip -p X.aab base/manifest/AndroidManifest.xml | strings | grep -oE "app\.[a-z]+\.twa"
keytool -printcert -jarfile X.aab | grep SHA1
```

## OAuth 함정 3종 — 에러 메시지가 원인을 오도한다

**1. `youtubeSignupRequired` ≠ 채널 없음**
`youtube.upload` **단독 scope**면 API가 소유 채널을 식별하지 못해 "채널이 없다"는 뜻의 에러를 던진다. 실제로는 채널이 있었다.
→ `youtube.readonly`를 함께 요청한다.

**2. `403 access_denied` — 테스트 사용자에 다른 계정을 등록**
게시 상태가 '테스트 중'이면 등록된 테스트 사용자만 인증할 수 있다. 등록한 주소와 인증을 시도한 주소가 **한 글자 달랐고**, 그걸 찾는 데 몇 시간을 썼다.
★ **오타가 아니었다. 두 계정 모두 실재했다.** 하나를 "오타"로 보고 정리했다면 다른 기능이 끊겼을 것이다.
→ 이메일은 눈으로 믿지 말고 **복붙**하고, 어느 계정인지 **매번 확인**한다.

**3. 테스트 상태의 refresh_token은 7일 만료**
자동화에 치명적이다. **프로덕션 게시가 필수.**
게시 버튼이 회색이면 브랜딩 페이지의 **개인정보처리방침·서비스약관 링크가 비어서**다. → `/privacy`, `/terms` 라우트를 앱에 직접 추가해 해결. 심사(verification) 없이 게시 가능하고, 인증 시 "확인되지 않은 앱" 경고를 한 번 넘기면 된다.

**진단 도구를 먼저 만든다**
토큰의 **계정·scope·채널을 한 번에 확인**하는 엔드포인트를 하나 둔다. **추측하지 말고 이걸 먼저 친다.**

## 잔액 소진으로 잠긴 계정은 충전해도 자동으로 안 풀린다

**증상**
`User is locked. Reason: Exhausted balance`. 충전해도 잠금이 유지된다(공급자 측 알려진 버그).

**영향**
영상 생성 프로바이더 14개 중 10개가 한 게이트웨이를 경유했다. **하나가 잠기면 파이프라인 대부분이 죽는다.**

**대응**
- 잔액을 넉넉히 유지하고 0 근접 전에 미리 충전한다
- **한 곳에 올인하지 말고 최소 1개는 별도 경로로 살려둔다**
- 잠기면 충전 재시도 대신 바로 지원 티켓

**해제 신호 (참고)**
첫 시도에서 즉시 403이 아니라 **타임아웃**이 난 것이 처리 중이라는 신호였다.

## 성능 다이어트가 '불안정' 체감으로 되돌아온다

**증상**
프레임을 지키려고 캐시·프리로드를 조였더니, 프레임은 유지됐지만 타일이 늦게 차서 화면이 비었고 **그게 버벅임보다 더 불안정하게 느껴졌다.**

**원인**
**로딩속도와 프레임은 다른 축**인데, 다이어트는 둘을 같은 손잡이로 착각하고 조인다.

**해법**
- 두 축을 **따로 측정**한다. fps와 **타일이 채워지는 시간**을 같이 본다
- 조이기 전에 **되돌릴 수 있게 값을 기록**해둔다. 나중에 원복이 가능했던 건 이전 로그에 값이 남아 있어서였다
- 로딩 인디케이터처럼 **기다림을 보이게 하는 것**도 체감 개선 수단이다(값을 안 건드리고)
